# Stateplane logical contract v1

Status: normative design for STA-2, 2026-09-23. No API endpoint or repository adapter is implemented here. All transports must map to these same application operations and envelopes; [reference conformance](../test/README.md) exercises an intentionally small in-memory oracle, not real PostgreSQL/Cloudflare behavior. Decisions and deferred operational ownership: [decisions.md](decisions.md).

## 1. Identity, placement and policy

`space = {id, ownerPrincipalId, homeCellId, placement:{cellId, storageTargetId, generation}, lifecycle, policyVersion}`. IDs are opaque stable strings, distinct from the account/principal/credential identifiers and physical storage IDs. Owner is a personal account principal; ownership transfer and team accounts are unsupported in v1. The owner can have several spaces and grant `{credentialId, collectionId, capabilities, expiresAt?}`; grants cannot grant ownership. Collection IDs are stable within a space. Capabilities include `schema:write`, `records:read/write`, `sources:read/write`, `claims:read/write/review`, `events:read`, `export:read`, and `space:admin`. All reads (including counts, receipt replay, events, search, export and source bytes) check current credential, lifecycle, policy and collection grants; links grant nothing. Owner access still requires a valid authenticated credential.

`active` accepts permitted reads/writes; `readOnly` permits reads/export and receipt replay but no new writes; `suspended` denies all content reads/writes including receipt replay; `deleting` denies new writes and content reads while erasure runs; `deleted` returns `NOT_FOUND` for ordinary callers. `space:admin` may inspect lifecycle metadata through a separate administrative operation; no content disclosure follows from that. Policy/grant/placement changes increment `policyVersion`/generation under authority, invalidate old routing assertions/cursors, and must be fenced at commit as well as request start. A client's `spaceId` is a requested selector. Global routing validates identity, looks up allowed placement, issues short-lived signed audience/destination/generation context; the destination validates assertion and current policy against authority. No direct-cell credential or stale cache is authorization. A placement move preserves all public IDs.

## 2. Collection schema: published JSON Schema syntax

Published syntax is **JSON Schema Draft 2020-12**, restricted to the listed keywords; there is no custom `fields` DSL translation. The definition carries `{slug, version, schema, unique:[{name,paths}], filterable, sortable, lifecycle?}`. `schema` must be a closed root object (`type:object`, `additionalProperties:false`) and may have nested closed objects to a configured depth. Allowed validation keywords: `$schema` (exact Draft 2020-12 URI), `type`, `properties`, `required`, `additionalProperties:false`, `items` (single homogeneous schema), `minItems`, `maxItems`, `minLength`, `maxLength`, `minimum`, `maximum`, `enum`, `format:"date-time"` for RFC3339 UTC timestamps, and `description`. Types: string, integer, number (finite), boolean, object, array, or nullable scalar union `[T,"null"]`. Null is explicit data, missing means absent; required tests property presence, not truthiness. Reject all other keywords including `$ref`, combinators, `patternProperties`, defaults/coercion and unknown formats with `SCHEMA_UNSUPPORTED` at definition time (do not silently ignore). Empty schemas/recipes must still obey closed objects and configured size/depth budgets. Numeric/byte budgets are configuration gates owned downstream, not invented constants here.

Keyword values must also be well formed at definition: length/item limits are nonnegative integers with minimum no larger than maximum; numeric bounds are finite numbers in ascending order; `enum` is a nonempty array of values valid for its declared shape (including null only when nullable), `description` is a string, and types have no duplicates. Invalid keyword shapes, conflicting bounds and unsupported constraints fail `SCHEMA_UNSUPPORTED` before collection creation/revision; invalid record values fail `SCHEMA_INVALID`. `minLength`/`maxLength` count Unicode codepoints (not UTF-16 code units or bytes). The configured size/depth budgets remain separate from schema keyword values.

Initially only compatible additive schema revisions: add a **top-level** optional field (including documented nullable representation), change descriptions, or add top-level filter/sort fields *after* typed-index backfill and ready flag. Adding a field inside an existing nested object or array item is `SCHEMA_BREAKING` in v1, even if optional; a future migration workflow may broaden this. Existing accepted rows keep `schemaVersion`; reads do not rewrite them. A write validates the **current** schema and uses the current version. An addition to `required`, a changed type/enum/constraint/normalizer, removed field, narrowed bound, or new uniqueness over existing data is `SCHEMA_BREAKING` until an explicit migration workflow exists. Schema update requires expected collection version, `schema:write`, and commit-time schema version check; unsupported and breaking revisions fail without changing rows. A collection lifecycle rule may specify allowed enum transitions on a declared field; if present, create and replace/patch enforce declared transitions at commit. Rule changes are breaking in v1. No domain-specific baked-in lifecycle.

## 3. Records, keys, links and transactions

String inputs used as external keys and record values must be sequences of Unicode scalar values: reject unpaired UTF-16 surrogates rather than replacing them during UTF-8 encoding or NFC normalization. Invalid external keys fail `INVALID_ARGUMENT`; malformed string data (including composite-unique components) fails `SCHEMA_INVALID` before any reservation, record, event or receipt change. Definition property names and declared unique-constraint names must likewise be well formed (`SCHEMA_UNSUPPORTED` otherwise). Unique-constraint names are nonempty and **distinct within each collection**; duplicate names fail `SCHEMA_UNSUPPORTED` before the collection is created. Distinct names identify independent reservation namespaces, even if their path values cross-match. No global constraint-name uniqueness is required.

Create is create-only (`records_create`); generated keys use canonical record ID as key and cannot be supplied by the caller. External keys are supplied on create, must be nonempty UTF-8 strings, normalized by Unicode NFC then stripped of surrounding Unicode White_Space, with no case folding; if normalized empty, reject `INVALID_ARGUMENT`. The fixed trim set is U+0009–U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000–U+200A, U+2028–U+2029, U+202F, U+205F and U+3000 (not ECMAScript `trim`: U+FEFF is **not** trimmed). Only edge characters are removed, after NFC. Persist normalized key and immutable key mode; do not normalize data fields unless explicitly declared by a future versioned rule. Record ID and external key cannot change on replace/patch/delete: existing-record mutations reject any `externalKey` input, even an identical normalized value, with `INVALID_ARGUMENT` before effects. Generated IDs and external keys occupy **separate typed namespaces**: a caller may choose an external key text equal to a generated ID without blocking ID allocation, and key lookup must specify mode or return an unambiguous canonical ref. Uniqueness of normalized external keys is `(spaceId, collectionId, key)`; no global uniqueness across collections/spaces. A declared composite `unique` constraint names ordered top-level scalar paths; each component is encoded with type tags and length-prefixing to avoid delimiter/type ambiguity. External-key and constraint-name reservations have separate typed namespaces, even for adversarial names or strings. If any component is absent or explicit null, no reservation for that tuple (two such rows may coexist). Otherwise compare NFC strings, exact booleans, canonical finite JSON numbers and UTC instants for date-time fields; constraint name plus tuple is unique per space/collection. `format:"date-time"` accepts real UTC calendar instants only (four-digit positive year, `Z`, valid date/time, no leap seconds or offsets in v1); canonical uniqueness removes trailing zeroes in fractional seconds, including `.0`, without truncating precision. Invalid calendar values fail `SCHEMA_INVALID`, and nullable enum fields still check the enum for explicit null. Unsupported paths/non-scalar components are rejected at schema definition. Tombstones retain external and composite reservations indefinitely in v1: key reuse fails `KEY_RESERVED`, not implicit resurrection. New generated IDs are always fresh. Restoration/reuse is unsupported.

`records_replace(id, data, expectedRevision, idempotencyKey)` replaces the entire user data, including removal of omitted optional fields; `records_patch(id, set, unset, expectedRevision, idempotencyKey)` is a **top-level** patch: set explicitly writes values including null, unset explicitly removes named optional fields, overlapping paths are invalid; no array indexing/deep merge. Validate the resulting full record against the current schema and any lifecycle rule. No-op replacement/patch still increments revision and produces audit/receipt/outbox to keep replay unambiguous. `records_delete(id, expectedRevision, idempotencyKey)` creates a tombstone with the next revision. Every existing-record mutation MUST carry a positive `expectedRevision` even if idempotency key matches a previous committed write. Create has no `expectedRevision`; an existing key never becomes an upsert. Stale revision gives `REVISION_CONFLICT`; missing/tombstoned target gives `NOT_FOUND` to authorized callers (except matching receipt replay). Concurrent writers serialize via conditional revision write; exactly one succeeds at a revision.

All record changes atomically commit canonical row/tombstone, all unique reservations/typed fields, immutable change event, idempotency receipt and projection outbox. A rejected request produces none. Commit-time auth/policy/placement/schema recheck prevents revocation or relocation races. `links_create` checks both endpoints exist, are in same space and are readable/writable under caller's owning collection grants; links carry explicit type and `restrict` or `detach` deletion policy. A record delete with live `restrict` links fails `LINK_RESTRICTED`; `detach` links tombstone atomically with the record and outbox. No implicit cascade of target records, source bytes or claims. Source/claim write and delete follow their own revision/receipt contract when mutable; originals are immutable.

For `records_patch`, each `unset` path must be a distinct, declared, top-level optional field in the current schema. Unknown, required, overlapping, duplicate, or non-string paths fail `INVALID_ARGUMENT` with no effects, even if deleting a nonexistent property would otherwise be a no-op. Removing an absent but declared optional field is a valid no-op patch and still advances revision.

## 4. Idempotency and receipt ordering

All mutations require an idempotency key; receipt identity is `(spaceId, credentialId, operation, idempotencyKey)` with a canonical request fingerprint over operation, target/collection, normalized key, payload including explicit null versus absence, optional **caller-supplied** `expectedSchemaVersion` (absence is distinct from a value) and `expectedRevision`; authenticated actor/credential identity is server-derived and included. Do **not** fingerprint the server's current schema version: compatible additions after a committed write must not invalidate a lost-response replay. A new write supplying `expectedSchemaVersion` requires an exact current collection version match (`SCHEMA_CONFLICT` otherwise), after receipt lookup and before mutation; omission means validate against the current schema. Canonicalization sorts object-property names by their UTF-8 bytes, not locale/ICU collation (including nested objects and numeric-looking names), preserves array order, and distinguishes types, set/unset, and absent/null. Concurrent same identity is serialized on a unique receipt reservation. At request entry authenticate and resolve space; **authorize the requested target operation against current policy first**, including visibility of its collection, and check lifecycle. If an unexpired receipt identity exists, also authorize the **original receipt target and owning collection** against current policy before comparing its fingerprint or returning any receipt information: a still-authorized collection must not reveal a revoked collection's receipt through same-key mismatch. Different payload under same identity yields `IDEMPOTENCY_MISMATCH` (no mutation); matching committed receipt returns original canonical result with `replayed:true`, even if `expectedRevision` or the optional schema precondition is now stale or target has since changed/deleted, provided current authorization still covers the original target. Matching pending receipt waits on/returns a retryable `RECEIPT_PENDING` without executing another write. Only after receipt lookup do ordinary schema/revision conflict checks run. No receipt or result disclosure after credential/collection revocation; suspended/deleting spaces deny it. Receipt replay does not enqueue a second outbox event or falsely upgrade projection freshness; historical receipt remains immutable, `replayed` is response metadata.

Retention duration is not selected here. Implementers must configure/document it, expose expiry via `expiresAt` on every receipt and retain at least their promised client retry window. After expiry, the same key is a **new** request and may fail stale revision or unique reservation; never promise indefinite exactly-once retries. A committed mutation followed by a lost HTTP response can be safely retried before expiry. Auth failure, mismatch and rejected writes must not consume a successful receipt identity.

Receipt envelope: `{contractVersion:"1", receiptId, spaceId, ref:{kind,id}, operation, beforeRevision, revision, schemaVersion, committedAt, expiresAt, projection:{generation,state:"pending"|"current"|"degraded"}, replayed}`. `beforeRevision` is null for create, otherwise prior revision. Delete returns tombstone revision. A later `projection_status(ref)` reports actual observed generation/revision and job failures; the original receipt is not retroactively rewritten. Timestamps/IDs are assigned by authority; tests use deterministic synthetic values only as oracle examples.

## 5. Queries, cursors, counts and snapshots

Exact get/key lookup, typed filter query, count and exists execute against authority and only visible live records. Count returns exact number matching the same policy/filter at its statement snapshot, not a rounded vector estimate; exists returns boolean, stops once a match exists. They describe **one query instant**, not completeness across paginated requests. Filter and sort fields/operators are allowlisted per schema (`eq`, `lt`, `lte`, `gt`, `gte`, `in`, `isNull` on compatible scalar types); bounded filters, `AND` only initially, no raw SQL/free-form JSON operators. Null and missing differ: `isNull` matches explicit null only; absent field never equals null. Default ordering is `(createdAt ASC,id ASC)`; an explicitly allowed scalar sort has ascending precedence `missing < explicit null < value`, with values in typed order (numbers numerically, booleans false before true, strings by unnormalized UTF-8 byte order, UTC instants chronologically at full fractional precision). Descending reverses the *entire* primary order (`value > null > missing`), including value comparison, but the stable `id ASC` tie-breaker never reverses. The keyset position is `(presence rank, typed value if present, id)` for explicit sorts, or `(createdAt,id)` by default; the cursor resumes strictly after that tuple in the requested direction. Two missing values and two nulls remain distinct records ordered by ID. Each query must include space + collection + current grants.

`records_query` returns live **keyset** pages. Opaque authenticated cursor binds actor credential, space, policy version, collection, schema version, filter/sort digest, last sort tuple/ID, placement generation and expiry. Any mismatch/tamper/expiry fails `CURSOR_INVALID`, not an unscoped scan. Resume strictly after the last tuple. Inserts/updates/deletes between pages can change the visible result; duplicates or omissions from records moving across a sort boundary are possible, and live pagination MUST NOT be advertised as a complete snapshot. Cross-space or revoked cursor fails auth before cursor decoding/disclosure. No offset pagination.

For complete export/long analysis use a pinned consistent snapshot/watermark and resumable job ID bound to authorization and placement generation; subsequent pages derive from that *same* committed boundary, include delete/schema/grant policy handling, and enforce expiry/cancel. A logical update sequence or materialized immutable manifest may implement it; a mere `updatedAt <= watermark` filter on current rows is **not** sufficient. Results and blob access reauthorize at fetch; revocation cancels content access even to an already materialized manifest. Bounded typed count/group/aggregate/time buckets may operate on one authoritative statement snapshot; explicit export/analysis snapshot is required for repeatable multi-page totals. Snapshot mechanics, retention and budgets belong to downstream implementation issues.

## 6. Evidence, retrieval and errors

A source has immutable digest, capture/observation time, MIME kind and original pointer or explicit `referenceOnly`; no URL is proof of fetched bytes. Sources and claims each have one owning collection and access inheritance; linked evidence cannot broaden access. A claim contains text/assertion, actor, source refs, observed/valid time, revision and `unreviewed` or explicitly reviewed status; automatic extraction can produce candidate claims/evidence offsets only. It never patches records. Search uses Postgres full-text + pgvector candidate projections, and must reread, filter, authorize, verify revision/tombstone and present canonical refs/provenance. A candidate cannot answer authoritative status/count/completeness without a separate exact query. Freshness is `current` only when indexed authority revision and generation match; otherwise `pending` or `degraded` with component status. Rebuild from authority into a new generation, cut over after verification; a stale async job cannot resurrect deleted refs.

Stable code -> HTTP mapping: `INVALID_ARGUMENT`/`SCHEMA_INVALID`/`SCHEMA_UNSUPPORTED`/`SCHEMA_BREAKING` 400; `UNAUTHENTICATED` 401; `FORBIDDEN` 403; `NOT_FOUND` 404; `REVISION_CONFLICT`/`UNIQUE_CONFLICT`/`KEY_RESERVED`/`LINK_RESTRICTED`/`IDEMPOTENCY_MISMATCH`/`SCHEMA_CONFLICT` 409; `CURSOR_INVALID` 400; `SPACE_UNAVAILABLE` 423; `RECEIPT_PENDING`/`PROVIDER_UNAVAILABLE` 503. Errors are `{contractVersion:"1",error:{code,message,retryable,requestId}}`, no record data or credential details. Wrong-space IDs may return `NOT_FOUND` to avoid confirming existence; permission checks before receipt/cursor inspection prevent leak. MCP structured error, CLI nonzero exit and UI actionable alert preserve code and requestId; no transport can bypass application policy. Index degradation must not convert successful authoritative writes to failed writes.

## 7. Same operation across transports

Example only (generic): collection `entries` uses schema `{"$schema":"https://json-schema.org/draft/2020-12/schema","type":"object","properties":{"label":{"type":"string"},"state":{"type":"string","enum":["open","closed"]}},"required":["label"],"additionalProperties":false}`. A caller authorized for space `sp_alpha` creates `{externalKey:" item-1 ",data:{label:"Item 1",state:"open"},idempotencyKey:"req-a"}`; authority stores key `item-1`. HTTP `POST /v1/spaces/sp_alpha/collections/entries/records` body supplies that input; MCP `records_create` accepts `{spaceId,collectionId,externalKey,data,idempotencyKey}`; CLI `stateplane records create --space sp_alpha --collection entries --key ' item-1 ' --data '{"label":"Item 1","state":"open"}' --idempotency-key req-a`; UI form selects the same space/collection and submits the same fields with a generated retry key. Each receives the same canonical receipt fields for the same credential/request (UI is not assumed to reuse another client's credential/key). `records_replace` through every surface must send `expectedRevision:1`, not an upsert; retry of a committed replacement with revision 1 returns its saved receipt before stale rejection. UIs show returned revision and pending projection state; clients display `REVISION_CONFLICT` instead of silently overwriting. API routes/tool names here are proposed public shapes for downstream transport implementation, not evidence that any currently run.
