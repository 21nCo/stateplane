# Stateplane logical contract v1 — foundation

Status: normative design for STA-2, 2026-09-24. This repository does not implement a deployed service. This document fixes identity, placement and collection-schema semantics for all transports. The version identifier is `contractVersion: "1"`; an incompatible future contract requires a new version and conformance cases. See [decisions](decisions.md) for rationale and unresolved implementation choices. Mutation, query/snapshot, transport and executable adapter contracts extend this foundation rather than weakening it.

## 1. Spaces, identity and regional placement

The domain-neutral space is a personally owned state container:

```text
space = {
  id, ownerPrincipalId, homeCellId,
  placement: {cellId, storageTargetId, generation},
  lifecycle, policyVersion
}
```

`id` is an opaque, stable public logical identifier, never an account ID, credential ID, regional hostname or database ID. `ownerPrincipalId` identifies a personally authenticated account principal; an account may own several spaces. `homeCellId` is the selected logical home/serving cell, while `placement` is the authoritative *physical* storage target and monotonically advancing routing generation. The home-cell concept and storage placement are deliberately distinct so relocation or later dedicated databases preserve public IDs, collection IDs, refs and owner. The control plane resolves placement; it does not become the records database. Team ownership/transfer and active-active writes are not supported by v1; there is one fenced authoritative writer placement at a time. No caller-provided cell URL or space selector is an authorization assertion.

Every collection belongs to exactly one space, with stable collection ID, slug and current schema version. An owner can grant `{credentialId, collectionId, capabilities, expiresAt?}` to agent credentials; a grant does not transfer ownership and one credential can have independent grants for multiple collections. Capabilities include `space:admin`, `schema:write`, `records:read`, `records:write`, `sources:read`, `sources:write`, `claims:read`, `claims:write`, `claims:review`, `events:read` and `export:read`. Caller scope is derived from authenticated credential, not from model-controlled arguments; even an owner needs an active credential. Policy checks use the owning collection for a ref and cannot be broadened by a link, search hit or provider tag.

Space lifecycle is `active` (authorized operations allowed), `readOnly` (new writes denied; reads/export permitted and an already committed receipt may be replayed only under current original write grants), `suspended` (content reads/writes/replay denied), `deleting` (new writes/content reads denied while erasure runs), or `deleted` (`NOT_FOUND` to ordinary callers). A separate authorized administrative operation may inspect lifecycle metadata; it does not grant content access. Policy/grant changes increment `policyVersion`; placement changes increment placement `generation`. Routing, cursors and writes must be invalidated/fenced on changes. At the global entry, authenticate and resolve current space/grant/placement, then issue short-lived, signed audience/destination/space/generation routing context. The destination cell revalidates the assertion and current policy against authority; a mutation checks again at commit. Stale caches or direct-cell credentials cannot override revocation or move fences. Failure of permitted placement must not silently move data across regional boundaries. Expiry and cache strategy remain downstream operational choices.

## 2. Collection schema syntax and bounded subset

The *published* definition syntax is JSON Schema **Draft 2020-12**, not a custom `fields` DSL. A collection definition carries `{slug, version, schema, unique:[{name,paths}], filterable, sortable, lifecycle?}`. `schema` is a closed root object: `type: "object"`, `properties` and `additionalProperties: false`. Nested objects, including array-item objects, must also be closed; recursive/deep structures remain subject to configured depth and byte budgets. Every definition and revision is checked before effects. `schema:write` and expected collection version are required to revise it; record-write permission alone is insufficient.

Allowed schema validation keywords only: `$schema` (exact URI `https://json-schema.org/draft/2020-12/schema`), `type`, `properties`, `required`, `additionalProperties: false`, `items` (one homogeneous item schema), `minItems`, `maxItems`, `minLength`, `maxLength`, `minimum`, `maximum`, `enum`, `format: "date-time"` (RFC 3339 UTC instant) and `description`. Allowed types are string, integer, finite number, boolean, object and array; only scalar nullable unions `[T, "null"]` are allowed. `integer` is bounded to exactly representable binary64 safe integers, inclusive ±9007199254740991; this is a JSON-interoperability rule, not an arbitrary storage quota. String lengths count Unicode code points, not JS UTF-16 units. `required` tests presence: an explicitly null value is not missing and is valid only for a nullable type and an enum that permits it. Object/array sizes, nesting, field counts and payload bytes must also be bounded by downstream documented configuration; this design assigns no numerical defaults to those budgets.

All keyword values must be well formed: nonnegative integer length/item limits in ascending order, finite numeric minimum/maximum in ascending order, nonempty enum array of values valid for the declared shape (including null only when nullable), string description, no duplicate types, valid Unicode scalar-value property names and no unsupported keyword/format. Unknown keywords (`$ref`, combinators, `patternProperties`, `default`, coercion and any unlisted keyword included) or malformed definitions fail `SCHEMA_UNSUPPORTED`, not silent ignore or delayed runtime error. Valid definition but invalid record data fails `SCHEMA_INVALID`, before any write effect. No schema description or recipe is a permission to inject a default value into an authoritative record.

Initially compatible revision changes are **top-level optional field additions** and description annotations. Newly declared top-level filter/sort fields are compatible only after a typed index backfill and ready flag; until ready, the query compiler must not use an index as if complete. New nested optional properties or array-item fields, required additions, removed fields, changed types/enums/constraints/normalizers, narrowed bounds and new uniqueness over existing data are `SCHEMA_BREAKING` until an explicit migration mechanism exists. Compare structural property *names* literally, including a field named `description`; only annotation keywords named `description` are ignored for compatibility. No old record is silently rewritten on revision: each retains accepted `schemaVersion`; new writes validate against the current schema, and commit checks the expected collection version. A collection lifecycle rule, when configured, specifies enum transitions on a declared field and is checked at commit; changing the rule is breaking. There is no built-in domain-specific lifecycle.

The definition's `unique` entries have nonempty, distinct names within the collection; each `paths` list names ordered, declared **top-level scalar string paths** (never numeric/coerced or dotted paths). `filterable` and `sortable` likewise list only declared supported top-level scalar paths. Malformed paths, duplicate unique names, or unsupported declarations fail `SCHEMA_UNSUPPORTED` before the definition is stored. External-key and named-composite uniqueness are scoped to `(spaceId, collectionId)` and use separate typed reservation namespaces; they are not global. Missing or explicitly null components create no composite reservation, but missing and null remain distinct record values. Composites encode ordered components with type and length boundaries rather than concatenating strings. For composite *comparison only*, non-null strings are normalized to Unicode NFC (no trimming or case folding); their stored record values remain byte-for-byte as submitted, so canonically equivalent strings may collide in uniqueness while exact data reads return the originally supplied spelling. This is an index-key transformation, not silent record normalization. Non-string components preserve typed meaning; UTC date-time components compare by canonical instant. The mutation contract must specify reservation lifetime and conflict errors; the adapter must test this invariant against real Postgres.

The machine-readable [generic definition example](examples/entries.v1.json) is ordinary versioned registry data, not a shipped workflow recipe. Its `label` uniqueness deliberately exercises the NFC comparison boundary while the stored `label` spelling stays unchanged. Consumers can load this fixture without parsing Markdown.

## 3. Contract boundaries and verification

The fixed physical schema holds spaces/placements/grants, collection versions, JSON records, typed field indexes and unique reservations, sources, claims, links, audit/events, idempotency receipts and projection outbox. Collection creation inserts registry data, never a table, database, Worker or MCP tool per collection. The authoritative regional Postgres path through Hyperdrive must have query caching disabled for fresh policy/exact reads and conditional transactions; native full-text and pgvector are rebuildable projections, and an interchangeable embedder sits outside the write transaction. The real target adapter must prove atomicity, revision fencing and unique reservations; documentation/in-memory examples are not evidence of provider readiness.

The subsequent mutation contract owns create-only and revision-checked replace/patch/delete, null-vs-missing write behavior, generated/external key normalization, tombstones, links, receipt/idempotency order and errors. The subsequent query contract owns exact count/exists, typed filters, live keyset cursors, consistent export/analysis snapshots, projection freshness and source/claim access. HTTP, MCP, CLI and UI must implement one logical application contract with no transport-specific authorization or mutation semantics. Exact record status and completeness are answered by authoritative queries alone; memory extraction may create attributed claims but never change records implicitly. Decision ownership and unselected operational parameters are tracked in [decisions](decisions.md).
