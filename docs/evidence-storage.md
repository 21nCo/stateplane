# Evidence storage schema (STA-13 slice 1)

Migration `040_evidence_storage.sql` adds the Postgres tables for sources, original objects, upload grants and attempts, extraction versions, claims and typed links. STA-33 adds the source, original and upload services described in [Sources, originals and upload grants](#sources-originals-and-upload-grants-sta-33). No HTTP, CLI or MCP operation exposes them yet (STA-37), and extraction, claims and links have no service yet (STA-34 to STA-36). The [v1 contract](../contracts/v1.md) §3 and §6 stay normative.

## Ownership and scope

Every row carries `space_id` and its owning `collection_id`, and every foreign-key path ends at `collections(space_id, collection_id)`. Sources and claims keep their canonical identity, revision and tombstone in the existing `entity_refs` table (migration 002). `sources` and `claims` hold their payload, with a kind-checked foreign key to that identity. A deferred constraint trigger on `entity_refs` makes sure that, at commit, each source identity has its source row and each live claim's current revision exists. Claim evidence may cite a source in another collection of the same space. A link endpoint must be in the link's space, and its owner must be one of its two endpoint collections. Citing or linking grants no access: service slices must authorize every endpoint and cited source against the caller's own collection grants.

| Table | Contents | Mutability |
| --- | --- | --- |
| `sources` | Locator (never proof of fetched bytes) and creating actor | Immutable; lifecycle via `entity_refs` |
| `original_objects` | One per source: `sha256`, `byte_size`, `mime_type`, `captured_at`, `observed_at`, `reference_only`, `object_key` (migration 041) | Immutable |
| `source_upload_grants` | Actor, collection, MIME, `max_bytes`, optional expected digest, expiry, then either revocation or finalization | Binding immutable; ends once, then final |
| `source_upload_attempts` | Staging blob key, observed digest, size and MIME, state, failure code, staging removal | Forward-only state; observations set once |
| `extraction_versions` | Parser, parser version, content, source offsets, cited original digest | Immutable |
| `claims` | Creating actor | Immutable; lifecycle via `entity_refs` |
| `claim_revisions` | Statement, attribution, observed and valid times, review status and reviewer | Immutable |
| `claim_evidence` | Cited source, optional extraction version and content range per revision | Immutable |
| `links` | Type, `restrict`/`detach` policy, typed `record`/`source`/`claim` endpoints | Tombstone only |

A source always has its original: `sources_original` is a deferred foreign key, so both rows commit together. A reference-only original has no digest or size, which discloses that no bytes were fetched. Its source must then have a locator, because nothing else points to the evidence; inserting a reference-only original for a source without one fails with `23514`, constraint `original_objects_reference_locator`. A stored original needs no locator. A stored original needs a digest, size and lowercase MIME type essence. Migration 041 adds `object_key`, the blob key of the original's bytes in the space's storage target: required for every new stored original, absent for a reference-only one (`original_objects_object_key`), and unique within a space, so two originals never share bytes. The digest identifies the bytes; the key locates them. An extraction version cites the exact original digest it parsed, so a reference-only source cannot have one. Versions and claim revisions start at 1 and have no gaps. A corrected extraction is the next version; earlier versions stay readable. Review produces a new claim revision. `accepted` and `rejected` require a reviewer and review time, and `unreviewed` is the default.

## Immutability and erasure

Triggers reject UPDATE, DELETE and TRUNCATE on `sources`, `claims`, `original_objects`, `extraction_versions`, `claim_revisions` and `claim_evidence`, and DELETE and TRUNCATE on `links`. A source's locator and a source's or claim's creating principal, credential and time are provenance, so they never change; deletion and revision live in `entity_refs`. A link may change only from live to tombstoned, with the next revision and a tombstone time; its endpoints, type, policy and owner never change, and it is never resurrected. As with record events, one exception exists: the table owner may delete rows while running the `stateplane_purge_space` SECURITY DEFINER routine for that one `deleting` space. Setting `stateplane.erasing_space` as a non-owner role does not bypass the guard. The purge routine removes evidence rows before the records and identities they cite, and `PostgresSpaces` reports a space erased only when no evidence row remains. Original bytes and staging blobs live outside the database, so removing them is a separate retention step (STA-36). Removing the metadata alone is not proof that bytes or backups are gone.

## Upload ledger

The upload tables are a ledger that moves forward only, enforced by a `BEFORE UPDATE` trigger on each. A grant's actor, collection, MIME type, `max_bytes`, expected digest, issue and expiry times never change. It ends exactly once, by revocation or by finalization with the committed source, and then no column changes. An attempt's staging key and start time never change. It may move from `receiving` to `verified`, and from either to `committed` or `failed`, but never back, and a committed or failed attempt keeps its state. The observed digest, size and MIME type, the failure code and the staging removal time are each set at most once, and a committed or failed attempt records nothing more except its staging removal. Only `updated_at` changes freely. A refused change fails with `23514` and constraint `source_upload_grants_transition` or `source_upload_attempts_transition`. Rows are never deleted outside space erasure; STA-33's upload service and reconciliation only advance them.

## Links and endpoint deletion

The database enforces the contract's "no live dangling link" rule. Tombstoning a record or `entity_refs` row while a live `restrict` link touches it fails with SQLSTATE `23001` (`restrict_violation`, constraint `links_restrict`). Mixed policies fail the same way. While only live `detach` links remain, the deletion fails with `23503`, constraint `links_detach`. The writer must tombstone those links, with their events and outbox entries, in the same transaction before the endpoint. Creating a link to a missing or tombstoned endpoint fails with `23503`, constraint `links_live_endpoint`.

No shipped surface creates links yet, so these errors cannot occur in production at this migration. The service layer does not map them yet either. If one reached `PostgresAuthority` today, a record delete would surface `23001` as the retryable `PROVIDER_UNAVAILABLE`, because the code is unmapped, and the record write path would turn any `23503`, including `links_detach` and `links_live_endpoint`, into `SCHEMA_CONFLICT`. STA-36 (STA-13 slice 5/6, links, deletion and retention) must do the following before any link-creating surface ships. It must map `links_restrict` to the non-retryable `LINK_RESTRICTED`, including in the batch item failure classifier. It must tombstone incident `detach` links, with their events and outbox entries, in the record and entity delete transaction before the endpoint. It must also stop collapsing `links_*` `23503` errors into `SCHEMA_CONFLICT`, and add a `PostgresAuthority` test that tells these outcomes apart.

A new link rewrites both live endpoint rows in place without changing any value. Because that is a real write, not only a row lock, it conflicts with the update that tombstones an endpoint at every isolation level, including a mix of levels. Under READ COMMITTED, whichever transaction runs second waits and then sees the other's commit. A REPEATABLE READ or SERIALIZABLE transaction whose snapshot predates the other's commit fails with `40001` instead, and its writer retries it like any serialization failure. The invariant therefore does not depend on `default_transaction_isolation`, and deleting an endpoint with no links succeeds at every level. The guard itself refuses an endpoint its rewrite cannot see, instead of leaving it to the foreign key. A foreign key checks only that the row exists, so it would accept an endpoint that a concurrent transaction created and tombstoned while the link waited on its other endpoint. An endpoint created by a transaction that has not committed when the link reaches it is therefore refused too. Link creation also serializes with ordinary updates to its endpoint rows, and with other link creations on the same endpoint, until it commits. The two endpoints are rewritten in a fixed order (kind, collection, id, in byte order), so links created in opposite directions between the same endpoints queue rather than deadlock. A writer that creates links still treats `40001` and `40P01` as retryable, because its other statements in the same transaction can take row locks in any order. The rewrite touches only `revision`, which no column-specific trigger watches, so it emits no record events and changes no projection. It does queue the deferred `entity_refs_payload` check for a source or claim endpoint, which the unchanged row passes. The guard functions run with owner rights, so operational roles can keep deleting records without link privileges.

## Bounds

These are initial integrity backstops, not measured provider limits. Extraction content, its offsets JSON and claim statements are each capped at 1,048,576 UTF-8 bytes, the same bound as canonical record data. Locators are capped at 4,096 bytes, attribution at 1,024, parser names, versions and link types at 256, staging keys at 1,024 and failure codes at 64. MIME types follow the RFC 6838 essence form with at most 127 characters per part. STA-33 records the text, upload and grant-lifetime bounds [below](#bounds-for-sources-and-uploads). Supported extraction MIME types and offset units belong to STA-34.

## Upgrade, restore and grants

Migration 040 creates empty tables and adds triggers to `records` and `entity_refs`. It scans no existing rows, so a populated upgrade needs no drained-traffic flag. It does take `SHARE ROW EXCLUSIVE` locks on `collections`, `records` and `entity_refs` until the migration commits. The migrator bounds that wait to five seconds. A busy record writer makes it fail and roll back without any 040 objects, and it is safe to retry. Like the rest of the migration history, 040 is forward-only: "down" means that rollback, not a reverse script. Triggers and foreign keys are post-data objects, so `pg_restore` loads rows first and then recreates the guards. The restore smoke checks that a restored original still rejects updates and that a restored `restrict` link still blocks deleting its record, then reapplies these grants to a nonowner role and reads every evidence table through it. Space deletion reads every evidence table to prove erasure before it publishes `deleted`, so the cell operational role needs `SELECT` on them now. After migration 040 and after every restore, run `pnpm db:grant-evidence` through the direct administrative connection with `STATEPLANE_CELL_ADMIN_URL` and the protected inventory's `STATEPLANE_CELL_ROLE`. It grants `SELECT` on the nine evidence tables, plus the STA-33 writes listed [below](#grants-and-verification), and reads each privilege back. Without it a nonowner role's purge still commits, but the deletion fails with `42501` before publication and stays retryable. Erasure itself needs no write privilege: it uses the purge routine. Evidence writes get their grants with the service slices that perform them.

Migration 041 adds `original_objects.object_key` with its checks and a unique partial index. No service wrote originals before it, but fixture rows may exist and originals are immutable, so `original_objects_object_key` is added `NOT VALID`: it binds every new row and scans none. A stored original from before 041 has no key and reads as missing bytes (`PROVIDER_UNAVAILABLE`). It takes an `ACCESS EXCLUSIVE` lock on `original_objects` only, bounded to five seconds by the migrator like 040, and a busy source writer makes it roll back and be safe to retry.

## Sources, originals and upload grants (STA-33)

`PostgresSources` (in `@stateplane/postgres`) is the application service for sources. `get` and `content` need `sources:read`. `ingestText`, `ingestReference`, `createUpload`, `upload`, `finalizeUpload` and `revokeUpload` need `sources:write`. Every call is admitted for the caller's own grant on the owning collection. Its transaction checks space, collection, policy version, placement and grant at the start and again before COMMIT, and rechecks the credential after the last statement, like record writes. The transports reach these operations in STA-37.

### Access

A source is read only through its owning collection. A source ID from another collection, asked through a readable one, is `NOT_FOUND`. An unreadable collection fails with `FORBIDDEN` whether or not the source exists, so it reveals nothing. `sources:write` alone grants no reads. A `readOnly` space or collection refuses new sources and grants with `SPACE_UNAVAILABLE`, but a retry of a committed ingestion still replays, as for record receipts. A `suspended`, `deleting` or `deleted` space refuses everything.

`content` evaluates authorization when the response starts. It authorizes the caller and reads the source, opens the original, and then checks the caller's authority and the source again before it returns the body. A credential revocation, a collection grant or policy change, a lifecycle change or a placement change while the original is being opened is refused, and the opened body is cancelled. A body already returned is not cut off by a later change.

### Original bytes

Original bytes live behind the `BlobStore` port (`@stateplane/application`). `R2BlobStore` (`@stateplane/storage`) implements it over the cell's R2 binding, `ORIGINALS`. Each original is stored under a key of its own, `originals/<base64url(spaceId)>/<grant>/<attempt>`, named after the upload attempt that promoted it and recorded in `original_objects.object_key` when that attempt commits. Identical bytes in two sources are stored twice; no object is shared, so removing one attempt's bytes can never affect another source (below). A write streams its body through a check that counts and hashes every chunk. It stores nothing unless the body has exactly the declared length and, when one is expected, the expected SHA-256. R2's put is atomic, so a refused or interrupted body leaves no object. In Workers the checked stream passes through `FixedLengthStream`, because R2 needs a known length. Every original is written with R2's `sha256` option, so R2 verifies the bytes and keeps the checksum on the object. Nothing ever writes different bytes under an original's key. `content` refuses an object whose size or stored checksum differs from the record, and it streams the bytes through a second check that errors the stream at the end if their digest or length differs. A consumer must treat that stream error as corruption. The published `@superfunctions/storage-r2@0.2.0` adapter is not used: it reaches R2 through the S3 API with account keys, not the regional binding, and its conformance is still pending ([package qualification](package-qualification.md)).

### Ingestion

- **Text.** Well-formed Unicode of 1 byte to 1 MiB in UTF-8, with a `text/*` MIME type (default `text/plain`), an optional locator and an optional UTC `capturedAt` that is not in the future. A string longer than 1,048,576 UTF-16 code units is refused before it is encoded, since UTF-8 needs at least one byte for each. The bytes are hashed in memory and pass through the same ledger as an upload: a 60-second one-shot grant with the exact size and digest, and an attempt recorded as `verified` before any byte is written. The staging key is never written.
- **Reference only.** A locator of at most 4,096 bytes is required, and a MIME type is optional. The locator is stored and never fetched. The original has no digest or size, which discloses that no bytes are held.
- **Upload.** `createUpload` issues a grant bound to the space, collection, principal and credential, one MIME type, a `maxBytes` limit, an optional expected SHA-256 and an expiry. `upload` declares the exact size, MIME type and an optional digest. A declaration that differs from the grant is refused before any attempt or byte exists. A grant takes a new attempt only while none of its attempts is `receiving` or `verified`; the grant row lock serializes that check, so a grant stages at most one live attempt of at most `maxBytes`. A failed attempt does not block a retry, and an upload whose verification transaction fails for any reason fails its own attempt before it returns, so the same grant accepts the retry. A writer that died mid-stream leaves its attempt `receiving` until reconciliation, so its caller revokes the grant and asks for a new one. The body then streams into `staging/<space>/<grant>/<attempt>`. It is counted and hashed, a `text/*` body must decode as UTF-8, and the write is cut off at the grant's expiry. A grant serves only its own credential; another credential gets `NOT_FOUND`. `finalizeUpload` names a verified attempt, an optional locator and an optional `capturedAt`. It copies the staged bytes to the attempt's original key, with R2 rechecking the digest, before the source metadata commits. Then it removes the staging object.

Request objects must be plain data objects, with `Object.prototype` or no prototype, whose own members are all enumerable data fields with documented string keys. Every other shape is `INVALID_ARGUMENT`: an accessor (which is never invoked), a symbol, non-enumerable or unknown member, an inherited field, an array or another prototype. A field given as `undefined` is supplied, not omitted, as `contracts/v1.md` defines for envelopes, so it is refused too, required or optional. A proxy, whether transparent, throwing or revoked, is refused with `INVALID_ARGUMENT` before any reflective read can run its traps, as `contracts/v1.md` requires of in-process adapters, and so is an upload body that is a proxy. A runtime without trap-free proxy detection refuses every in-process request object. An optional field takes its default only when absent: a supplied `null`, for example `expiresInSeconds: null`, is refused rather than read as the 300-second default. The collection is authorized first, and a refused request changes nothing.

Every decision on a request uses operations captured when the module loads, as `contracts/v1.md` requires of in-process inputs. Own keys and the allowed and required field lists are read by own index, never through `Array.prototype[Symbol.iterator]`, `includes` or `some`. Text is checked for NUL and lone surrogates by reading its UTF-16 code units, MIME essences are cut, trimmed and lowercased with captured `String` methods and matched with a captured `RegExp.prototype.exec`, digests are matched the same way, integers use a captured `Number.isSafeInteger`, and derived source IDs serialize their parts with a captured `JSON.stringify` applied to each string. A later change to any of those cannot drop a supplied digest, admit an unknown key, a missing field, an invalid MIME type or a fractional integer, or merge two source identities. Node's `Buffer` and `crypto` internals are trusted as the runtime provides them.

MIME verification compares media-type essences (lowercase `type/subtype`, parameters dropped) and checks UTF-8 for `text/*`. It does not sniff binary formats.

Each ingestion is idempotent without a receipt table, which references records only. A text or reference source's ID is derived from `(operation, credential, idempotency key)`, and an upload's from its grant. A retry finds the committed source and replays it with `replayed: true`. A different text, locator, MIME type or `capturedAt` under the same key fails with `IDEMPOTENCY_MISMATCH`. So does the same key in another collection, after that collection is authorized for the caller. An omitted `capturedAt` is the observation time and matches only another omission. Concurrent retries serialize on the source identity and commit one source. A replay does not expire. Issuing a grant is not idempotent: an unused grant simply expires.

### Upload failures and cleanup

| Event | Outcome | Cleanup |
| --- | --- | --- |
| Declared MIME, size or digest differs from the grant | `INVALID_ARGUMENT` | Nothing was created |
| Body longer or shorter than declared, wrong digest, invalid UTF-8 for `text/*`, or the body errors | `INVALID_ARGUMENT`; attempt `failed` with `length_mismatch`, `digest_mismatch`, `content_rejected` or `interrupted` | No object was stored; the staging key is deleted and its removal recorded |
| Grant expires while streaming, or before verify or finalize | `FORBIDDEN`; a streaming attempt fails with `grant_expired`. The statements that verify an attempt and finalize a grant check expiry themselves, so a request that waited on a lock or on R2's answer after reading its grant cannot verify or commit after expiry. | The writer removes its own staging; reconciliation removes the rest. No write to staging or to the original key starts after the grant's deadline (below), and a write the store confirms after it is reported as failed, so its own cleanup runs after it landed. |
| The caller's credential, collection grant, policy, placement or space lifecycle changes while streaming | The refusal (`FORBIDDEN`, `SPACE_UNAVAILABLE`, …); nothing is verified | The attempt fails with `refused_<code>`, for example `refused_forbidden`, and its staging is removed |
| Upload's verification transaction fails transiently (serialization, lock or time budget, provider or connection error, a database read timeout before COMMIT was sent) or its COMMIT goes unacknowledged | The error, retryable; an unacknowledged verification COMMIT is retryable `PROVIDER_UNAVAILABLE` once the attempt is released. Retrying the upload on the same grant starts a new attempt. If the attempt cannot be released, non-retryable `PROVIDER_UNAVAILABLE`, and the caller requests a new grant. | The body is consumed and the caller never received the attempt ID, so no later call could verify the attempt. It fails with `verify_failed` and its staging is removed, so the grant takes a new attempt. No original exists before finalize. An attempt that cannot be released stays `receiving` until reconciliation settles it after its grant ends. |
| Grant revoked (by its credential or the space owner) | `FORBIDDEN` for further uploads and finalize | Receiving and verified attempts fail with `grant_revoked` in the revoking transaction. After it commits, the verified attempts' originals and staging are removed; reconciliation repeats a removal that fails. A writer still streaming removes its own staging when it finishes. A finalize still copying bytes removes its original again when its commit is refused. |
| Finalize fails with a refused or deterministic error (authorization, lifecycle, expiry, identity conflict, missing or corrupted staging) | The error; corrupted staging is `PROVIDER_UNAVAILABLE` | The attempt fails with `commit_failed`, and its original and staging are removed. Another source or attempt with the same digest keeps its own bytes. A text ingestion's one-shot grant is revoked. |
| Finalize fails transiently (serialization, lock or time budget, provider or connection error, a database read timeout before COMMIT was sent, a read of staging that was interrupted) | The error; finalize may be retried. A database read timeout or lost session before COMMIT is retryable `PROVIDER_UNAVAILABLE`, since nothing committed; only an unacknowledged COMMIT is `COMMIT_OUTCOME_UNKNOWN`. | The attempt stays `verified` until its grant ends, then reconciliation settles it. If a revocation already failed it, its original is removed again at once. |
| Finalize COMMIT outcome unknown | `COMMIT_OUTCOME_UNKNOWN` | None. A retry replays the committed source, or reconciliation settles the attempt. |

A removal must never delete bytes a committed source relies on, even if its delete reaches R2 long after it was sent, for example after the remover's database session or Worker ended. Because no two attempts share an original key, this needs no lock. An attempt's key is referenced only by the `original_objects` row its own commit inserts, and only while the attempt is `verified` can that commit happen. Its bytes are removed only after a transaction that left the attempt `failed` has committed: the revocation, the failed finalize or upload's cleanup, or reconciliation. `committed` and `failed` are both final, so a delete, however late, targets bytes no commit uses or will use. A transition that rolls back leaves its attempt verified and its bytes intact. After the copy, and before the metadata transaction begins, finalize heads the object and requires the attempt's size and checksum; this head is bounded by the grant's deadline and holds no lock. If the object is missing, finalize fails with retryable `PROVIDER_UNAVAILABLE`, the attempt stays verified, and a retry copies the bytes again. Checking outside the transaction is enough: only a removal deletes the key, and only after the attempt's failure has committed, so the metadata commit, which locks the attempt and requires it to be `verified`, cannot commit once any removal of its bytes has started. A promotion that finds the object already present with a matching size and checksum, from an earlier finalize of the same attempt, does not copy it again. One that finds it missing copies it again from the attempt's own staging object, which stays until the attempt ends.

A revocation can fail an attempt while its finalize is still copying bytes, so that copy can land after the revocation removed the original. Three steps keep such an original from outliving its failed attempt:

1. **Writes end at the grant's deadline.** When an upload or finalize reads its grant row, it takes a local monotonic reading (`performance.now`) *before* sending the query and adds the remaining lifetime the database computes. The deadline is therefore never later than `expires_at`, and nothing after the read restarts the countdown. No write starts once the deadline has passed. After it, the body errors at its next chunk and at its end, so R2 can only store a body that had already ended before the deadline. A write the store confirms after the deadline is reported as `deadline`, not success.
2. **A failed finalize removes its original again.** A finalize that fails for any reason, including a `deadline` write, removes its attempt's original once the attempt's failure has committed. Because a `deadline` write is reported only once the store has answered, this removal runs after a late copy has landed.
3. **Reconciliation removes it once more.** A failed attempt that held a digest keeps `staging_removed_at` empty, even after its staging object is deleted, so it stays due for reconciliation. Reconciliation removes its original again after the grant's grace period, and only then records `staging_removed_at`. That covers a finalize that died or lost its connection between its copy and its own removal.

That last case is the only one whose cleanup depends on timing. A copy can still land after reconciliation's removal only if R2 acknowledges a PUT whose complete body (at most 25 MiB) it received before the grant expired more than 300 seconds later. No R2 limit we can cite bounds that acknowledgement, so the grace is a stated assumption, not a measured bound. Measuring R2's settlement of a put aborted after its body ended is part of the Cloudflare Preview acceptance.

Every sources transaction runs at `READ COMMITTED`, whatever the session's `default_transaction_isolation`. Each lock-then-read step, such as the grant and attempt row locks and the source-identity lock that serializes retries, must read rows committed before its lock was granted. A snapshot taken before the lock could miss them. A session that may still hold an open transaction or an unanswered statement, because BEGIN got no reply, a read timed out or COMMIT went unacknowledged, is discarded rather than returned to the pool, as `PostgresAuthority.transaction` does. A read timeout or lost session before COMMIT is sent is reported as retryable `PROVIDER_UNAVAILABLE`, so a finalize leaves its attempt `verified` for a retry. An upload's verification instead releases its attempt, as the failure table describes, because its consumed body cannot be verified again.

### Reconciliation

The cell jobs Worker's once-a-minute tick runs `SourceUploadReconciler.step` after projection dispatch and outbox reconciliation, in pages of 25 for up to 10 seconds. A page selects attempts whose staging is not yet removed and whose grant expired more than the 300-second grace period ago, through the `source_upload_attempts_staged` partial index. Each attempt settles in its own transaction under `FOR UPDATE SKIP LOCKED`. A `receiving` or `verified` attempt fails with `abandoned`. For any attempt that held a digest and did not commit, its original is removed as above. Then the staging object is deleted and `staging_removed_at` recorded. This covers writers that died mid-stream, finalizes that promoted bytes but never committed, copies that landed after a revocation, and staging that a committed or failed request could not delete. One attempt's failure does not stop the others. A failing attempt's `updated_at` is advanced in its own transaction, so it moves behind every due attempt not tried since. Attempts that keep failing therefore cannot hold the oldest page: each due attempt older than a healthy one is tried at most once before it, so the healthy one is reached within one tick per page of such attempts. The step reports all of them in one `AggregateError`, which the tick raises with any dispatch or outbox reconciliation error, and the failing attempt is retried on a later tick. A tick without the `ORIGINALS` binding fails before it opens a database connection. Attempts of a live grant are never touched. The upload ledger is never deleted outside space erasure, and erasing a space's original and staging bytes is STA-36's retention step.

### Bounds for sources and uploads

These are initial bounds with the evidence for each, not measured capacity. STA-19 measures deployed limits.

| Bound | Value | Evidence and purpose |
| --- | --- | --- |
| Text ingestion | 1 to 1,048,576 UTF-8 bytes | The bound already used for canonical record data and extraction content (migration 040). Text is hashed in one in-memory buffer, well within a Worker's 128 MB memory. |
| Upload `maxBytes` | 1 to 26,214,400 bytes (25 MiB) | Below the 100 MB request body limit of Cloudflare Workers on every plan ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/#request-limits)), so one streamed request carries an upload. Finalize streams the staged bytes through the Worker into the original key. That copy holds no transaction and is bounded by the grant's deadline (at most 900 s), not by the 30-second transaction budget. The copy rate is not yet measured. R2's single-put limit (5 GiB) is far above this. |
| Grant lifetime | Default 300 s, at most 900 s; text grants 60 s | Short-lived by design. A stream stops at its grant's expiry, so the lifetime bounds how long a writer can hold staging. |
| Reconciliation grace | 300 s after grant expiry | Lets a writer or finalize whose body ended before expiry get R2's answer and record its own outcome before reconciliation acts. Its deadline already ends at or before the expiry, so the grace covers only R2's acknowledgement of a body it has fully received, plus a timer firing late. That is an assumption to confirm on Cloudflare Preview, as described above. Staging can therefore outlive its grant by about the grace period plus one tick. |
| Reconciliation page and budget | 25 attempts per page, up to 10 s per tick, after the outbox's 20 + 10 s | Keeps each tick under its one-minute period. A page's attempts each take one short transaction and at most two R2 deletes. |
| Statements and locks | `READ COMMITTED`; 5 s per statement, 2 s per lock wait (`BACKPRESSURE`), 30 s per request | Same shape as the authority's short cell transactions. No transaction is held open across an R2 call: the copy, the head that precedes the metadata commit and every delete run outside one, so a slow or stalled R2 call never holds a row or scope lock that revocation, reconciliation or a space lifecycle change waits on. |
| Locator / idempotency key | 4,096 / 512 UTF-8 bytes | The schema's locator bound; the authority's key bound |
