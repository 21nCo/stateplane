# Retrieval projection storage (STA-44)

Migration `045_retrieval_projections.sql` adds the storage for rebuildable lexical and vector projections and makes authoritative evidence writes enqueue projection work. It is the first of six slices of STA-14: the embedding port and indexing worker (STA-45, [below](#indexing-worker-sta-45)), hybrid search (STA-46), context bundles (STA-47), generations, rebuild and model migration (STA-48) and transport, evaluation and docs (STA-49) follow. Application-level [hybrid search](#hybrid-search-sta-46) reads the active generations and application-level [context bundles](#context-bundles-sta-47) quote its reauthorized hits; there is no HTTP, CLI or MCP surface for either yet, and nothing starts or moves generations except SQL (STA-48 adds that).

Projections are derived, rebuildable data. Records, sources and claims stay independently readable without them. Every projection row names the canonical Ref (space, collection, kind, ID), authoritative revision and generation it was built from, so a later search can reread and reauthorize each hit at authority and reject stale or deleted ones. No projection row is evidence that its Ref is current, readable or complete.

## Tables

| Table | Contents | Mutability |
| --- | --- | --- |
| `retrieval_policies` | Per-collection policy versions: record fields (JSON Pointers), source extraction content, claim statements, lexical and vector switches, built-in text search configuration, allowed embedding processing regions | Immutable; versions start at 1 without gaps and are published in order, one successor of the current version at a time (even within one multirow `INSERT`; otherwise `retrieval_policies_order`, `23514`); the highest is current |
| `retrieval_collection_heads` | Per collection with a policy: its current policy version and the highest generation number it has allocated | Written only by owner-rights triggers, under an update lock, when a policy is published or a generation starts, so its policy version only advances and is always the highest; kept until erasure |
| `vector_index_strategies` | ANN strategy per accepted embedding dimension, with its evidence | Cell reference data, seeded by the migration |
| `projection_generations` | A collection's projection build under one policy version and, for vectors, one embedder, model, model version and dimensions | `building` → `verifying` → `active` → `retired`; `building` or `verifying` may be abandoned to `retired`. Each transition stamps its own time. Kept until erasure |
| `projection_refs` | Per generation and Ref: the authoritative revision (and source extraction version) its chunks were built from (for a Ref projected for the first time, are being built from), or that it was deleted | Moves forward only; a deleted Ref stays deleted; kept until erasure |
| `lexical_chunks` | A code-point range of one configured text, its content and a `tsvector` (GIN index) | Immutable; replaced by delete and insert |
| `vector_chunks` | The same Ref, revision, generation, offsets and policy, plus embedder metadata, processing region, digest of the embedded text and the embedding | Immutable; replaced by delete and insert |
| `embedding_checkpoints` | Embeddings computed outside SQL and saved before they are applied, keyed by the Ref's target revision and chunk; references the Ref's live `projection_refs` row in the generation | Immutable; removed when applied or superseded, and before the Ref is deleted |
| `projection_deletion_receipts` | A Ref removed from one generation: revision, chunks removed, time; references the Ref's deleted `projection_refs` row | Immutable; kept until erasure |
| `retrieval_outbox` | One unit of projection work per source extraction, claim revision and source or claim deletion | Delivery fields only; delivery is final; kept until erasure |

Every space-scoped table carries `space_id` and its owning `collection_id`; every key path ends at `collections`. `vector_index_strategies` is cell configuration and holds no space data.

## Chunk invariants

Each chunk row carries:

- **Canonical Ref**: `space_id`, `collection_id`, `ref_kind` (`record`, `source`, `claim`), `ref_id`.
- **Authoritative revision**: `revision` (the record or `entity_refs` revision) and, for a source, `extraction_version`. A chunk references its `projection_refs` row at exactly that revision and extraction while the Ref is live, so a chunk can never sit beside a newer revision or a deletion: advancing or deleting a Ref fails while older chunks remain. `projection_refs` names an existing record or `entity_refs` row (checked at COMMIT, like `projection_heads`, so applying takes no key-share lock on authority rows). Deleting a record or identity checks those foreign keys from the referencing side, once per deleted row, so `projection_refs` has partial indexes on the referencing columns (`projection_refs_record` on `(space_id, collection_id, record_id)`, `projection_refs_entity` on `(space_id, collection_id, entity_kind, entity_id)`); without them each check scans the table.
- **Generation and policy**: `generation` and `policy_version`, which must be the generation's own policy version. A generation is built under exactly one policy version, the collection's current one when it starts, so a policy change (fields, content or regions) takes a new generation. Publishing a policy and starting a generation both write the collection's `retrieval_collection_heads` row, and a generation reads its current policy and the last generation number from that row under an update lock before advancing it. So a generation whose transaction started before a newer policy or a higher generation committed is refused: under `READ COMMITTED` it waits for the other writer and then fails `projection_generations_policy` or `projection_generations_order` (`23514`); under `REPEATABLE READ` it fails with `40001`. A lower number can never start after a higher one, even once the higher one is retired.
- **Offsets**: `chunk_index`, `content_start` and `content_end` (code points in the projected text: the record field's value, the extraction content or the claim statement), and for a source optional `source_start` and `source_end` in the original. A lexical chunk's `content` is exactly its range. A record chunk names its `field`.
- **Embedder metadata (vector only)**: `embedder`, `embedding_model`, `model_version` and `dimensions`, which must equal the generation's, the region the embedding was processed in, which both the generation's policy and the collection's current policy must allow (so narrowing a policy's regions stops embedding in a removed region for every generation still being written, including the active one built under an older policy), and `content_sha256` of the embedded text. The embedding has exactly `dimensions` dimensions.

An insert trigger also refuses content the policy does not configure (an unlisted record field, source content or claim statements when switched off), a lexical chunk when lexical projection is off, a vector chunk or checkpoint when vectors are off, and any write into a retired generation. A vector chunk or checkpoint reads the current policy from the collection's head row under a share lock, so publishing a policy (or starting a generation) waits for embedders already writing, and an embedder that meets a newer policy is checked against it under `READ COMMITTED` or fails with `40001` under `REPEATABLE READ`; a `REPEATABLE READ` embedder whose snapshot predates any policy or generation start then retries. It computes `tsv` from `content` with the policy's built-in text search configuration, whatever the writer sends. Writes share-lock their generation row, so retiring a generation waits for writers already in it (they commit into it before it retires), and a writer that reaches the row while a retirement is in flight waits and is then refused: `23514` (`projection_generations_retired`) under `READ COMMITTED`, `40001` under `REPEATABLE READ`.

A Ref moves forward by revision, then deletion, then extraction version: deleting it at its current revision is forward whether the deleted row keeps or clears `extraction_version`, while a live row never moves to an older extraction and a deleted row never changes.

A deletion receipt needs the authoritative Ref deleted (a tombstoned record or `entity_refs` row) and, by foreign key, the Ref's `projection_refs` row in that generation deleted at the receipt's revision. A worker therefore marks the projected Ref deleted (an update of its live row, or an insert of a deleted row for a Ref the generation never projected) before recording the receipt. That row is the only fence between a receipt and an apply of the same Ref, and it holds under every isolation level: both write the same row or key, a deleted row never changes again and its key admits no second row. An apply whose snapshot predates a committed deletion fails with a serialization error (`40001`) under `REPEATABLE READ`, with the order check under `READ COMMITTED`, or with a unique violation (`23505`) if it inserts; a deletion whose snapshot predates a committed apply fails the same way or, under `READ COMMITTED`, deletes the newer revision after it. Once recorded, the Ref cannot be projected live in that generation again, including by a rebuild into a generation that has the receipt.

The same row fences embedding checkpoints, so no embedding of deleted text sits beside a receipt. A checkpoint references the Ref's live `projection_refs` row in its generation, at whatever revision that row is (a checkpoint is keyed by the Ref's target revision, which may be ahead of it). A worker therefore records the Ref in the generation before saving checkpoints: a Ref projected for the first time gets its live row at its target revision, with its chunks to follow, and advancing a Ref with checkpoints is allowed. Deleting the Ref is refused (`23503`) while any checkpoint of it in that generation remains, whatever the checkpoint's revision, so a worker removes the Ref's checkpoints with its chunks before deleting it, and the receipt follows only after that. A checkpoint is refused (`23503`) for a Ref the generation has not recorded or has deleted. Under concurrency: a checkpoint whose snapshot predates a committed deletion fails with `40001` under `REPEATABLE READ` and `23503` under `READ COMMITTED`; a deletion whose snapshot predates a committed checkpoint fails with `23503` at either level, because the deletion's check sees committed checkpoints; and a Ref recorded live and deleted by two transactions conflicts on its key (`23505`). A receipt covers one generation's projection rows only. It is not proof of erasure of authority rows, original bytes, other generations, WAL or backups.

## Projection work

Authoritative writes enqueue work in their own transaction, by owner-rights triggers, so no write path can skip it and a writer needs no outbox privilege:

| Authoritative write | Work |
| --- | --- |
| A new extraction version (STA-34 extract) | `source` `upsert` at the source's revision and the new extraction version |
| A claim revision: create (revision 1), revise and review (each a new revision) | `claim` `upsert` at that revision |
| A source or claim deletion (its `entity_refs` tombstone) | `delete` at the Ref's revision |

The work row records the space's placement generation at commit, as `projection_outbox` and `evidence_outbox` do. A rolled-back or refused write (for example a claim whose key loses its grants before COMMIT, migration 043) leaves no work; a replayed write inserts nothing and enqueues nothing. If the work cannot be enqueued, the authoritative write fails. Record writes already enqueue `projection_outbox` work in their transaction (migration 002), so records need no second queue. Deleting a source or claim also enqueues an `evidence_outbox` invalidation (migration 044); the retrieval queue is separate so its delivery state can be owned by the projection worker. The [indexing worker](#indexing-worker-sta-45) consumes `retrieval_outbox`; pending work is erased with its space.

Migration 045 enqueues, for evidence written before it, each live source's latest extraction and each live claim's current revision. Deleted evidence has nothing to project, and neither has a space being erased (`deleting`, or `deleted` awaiting an erasure repair). That also keeps an erasure already running migration 044's purge routine safe across the upgrade: it can wait on 045's locks and then resume with the old routine, which removes no retrieval work, so no work may reference its space's identities; it completes after 045 commits. A space whose erasure starts during the upgrade cannot reach that routine: before the backfill, 045 share locks every space it enqueues for, so an update of such a space's row (a lifecycle change such as `deleting`, or a policy, key or placement change) waits until 045 commits, and its purge then runs 045's routine; a space that commits `deleting` while that lock waits is rechecked and skipped. Those updates touch no table 045 locks, and a purge holds its space row only once the space is committed `deleting`, which 045 skips without locking, so this wait cannot deadlock; it is bounded by the migrator's lock wait like 045's table locks.

## ANN index strategy

| Dimensions | Strategy | Parameters |
| --- | --- | --- |
| 384, 768, 1024, 1536 | HNSW partial expression index `((embedding::vector(N)) vector_cosine_ops) WHERE dimensions = N` | `m = 16`, `ef_construction = 64` |
| 3072 | Exact distance within a generation's filters, no ANN index | — |

Evidence and reasoning:

- One `vector` column holds every dimension, so each recorded dimension has its own partial expression index; [pgvector's FAQ documents this pattern](https://github.com/pgvector/pgvector) for mixed dimensions. A generation must name a recorded dimension (foreign key), so an embedder with an unrecorded dimension needs a migration that records its strategy first. A query uses the index only with the same cast and `dimensions` predicate.
- HNSW rather than IVFFlat: IVFFlat derives its lists from the rows present when the index is built, and this migration builds on an empty table; HNSW needs no training step and accepts inserts incrementally. `m = 16` and `ef_construction = 64` are pgvector's defaults, not tuned values; STA-49's relevance evaluation measures recall and latency and may record different parameters.
- pgvector 0.8 refuses HNSW and IVFFlat indexes on `vector` columns above 2,000 dimensions (observed: `column cannot have more than 2000 dimensions for hnsw index`). 3,072 dimensions is therefore exact. Indexing it would need `halfvec` or reduced dimensions, a later decision.
- Cosine distance only, matching the operator class. The integration test confirms on PostgreSQL 17 with pgvector 0.8.7 that a 384-dimension nearest-neighbour query with the index's cast and predicate plans an index scan on `vector_chunks_hnsw_384`, and that, narrowed to one space, collection and generation, the planner may instead read that generation through the primary key and rank it exactly. A filtered ANN top-k is not complete recall: STA-46 must overfetch, report underfill and never treat either plan's result as complete.

These are storage choices on small local fixtures, not capacity, latency or recall measurements.

## Bounds

Initial storage bounds, chosen for bounded rows and validation, not measured provider limits: up to 32 record fields per policy, each a JSON Pointer of at most 256 bytes; up to 16 processing regions, each a lowercase label of at most 63 characters; lexical chunk content of at most 65,536 bytes (well inside PostgreSQL's 1 MB `tsvector` limit); embedder name up to 64 characters and model and model version up to 256 bytes; work errors up to 1,024 bytes. Chunk size, overlap, embedding retry and worker budgets are STA-45's [initial bounds](#bounds-of-the-worker).

## Upgrade, restore and grants

Migration 045 takes share row exclusive locks on `collections`, `records`, `claim_revisions`, `entity_refs` and `extraction_versions` up front, within the migrator's five-second bounded wait, and holds them until it commits. A writer holding them past the wait makes it fail with `Retrieval projection upgrade waits for record, extraction and claim writers; retry when long evidence transactions finish` and roll back completely (no table, trigger, ledger row or purge change); a retry applies it. Claim revise and review insert a revision before they advance the claim's `entity_refs` row, the order 045 locks in, so the step simply waits for them. A claim create writes its `entity_refs` row first; if one interleaves with the step, PostgreSQL resolves the cycle by aborting one side as a deadlock (`40P01`). When that is the migration, the migrator reports the same retry message; when it is the writer, that one request fails with the deadlock and nothing of it is written.

While the step holds its locks, record, source, extraction and claim writes wait for it. Apart from creating empty tables and indexes, its time is the enqueue backfill, which writes one `retrieval_outbox` row per live source with an extraction and per live claim. It reads every source and claim identity (`entity_refs`, live or deleted) and, per live identity, one primary-key probe for the source's latest extraction or the claim's current revision; it never reads older extractions or revisions, so their number does not change its time. Before running 045's SQL, the migrator takes the same locks in the same order and counts `entity_refs` rows up to 10,001. Above 10,000 identities it refuses with `Populated retrieval projection upgrade requires drained traffic above 10000 source and claim identities` and applies nothing, unless `STATEPLANE_POPULATED_INDEX_UPGRADE=drained` is set; set it only after stopping record, source and claim writers. Deleted identities count toward the bound because the backfill reads them.

Measured on local PostgreSQL 17 with pgvector 0.8.7 in Docker on an 8-core Apple Silicon host under load (load average 14 to 21), three runs each of the whole step in one transaction, rolled back (the step alone on an empty database takes 41 to 45 ms):

| Identities (half sources, half claims) | Live | Versions or revisions each | History rows | Enqueued | Step time |
| --- | --- | --- | --- | --- | --- |
| 10,000 | all | 20 | 200,000 | 10,000 | 279 to 615 ms |
| 10,000 | all | 100 | 1,000,000 | 10,000 | 341 to 456 ms |
| 10,000 | 10% | 100 | 1,000,000 | 1,000 | 61 to 84 ms |
| 100,000 | all | 2 | 200,000 | 100,000 | 3.4 to 3.7 s |

At the bound the writer stall is therefore at most about two thirds of a second, inside source and claim writers' two-second lock wait, after which they answer `BACKPRESSURE`; above it, it grows by about 35 microseconds per identity. The plan is a scan of `entity_refs` with a backward index-only scan of `extraction_versions_pkey` (or a `claim_revisions_pkey` probe) per live identity. These are local measurements, not Railway figures; measure the backfill on the target before relying on the bound there. The migrator's decision holds through commit, because the locks do. As for every migration in this repository (see [evidence storage](evidence-storage.md)), 045 is forward-only and "down" means transactional rollback, not a reverse script: the step is one transaction, and a step that fails or is refused leaves no table, trigger, ledger row or purge change and can be retried (`migration 045 rolls back atomically …` in `test/integration/retrieval-projections.test.js`). Recovery from a bad deploy is restore.

`stateplane_purge_space` now removes every space-scoped retrieval row before the records, identities and collections it references, and the space erasure report (`PostgresSpaces.erasure`) reads every space-scoped retrieval table (all but `vector_index_strategies`, which holds no space data) before reporting the database erased. The purge deletes `projection_refs` before the records and identities, in the same transaction, so at COMMIT each deleted record or identity runs one deferred foreign-key check against `projection_refs`; the referencing-side indexes keep each check an index probe. Measured locally (PostgreSQL 17 + pgvector 0.8.7, loaded 8-core host): a space with 4,000 records and 4,000 claims projected in three generations (24,000 `projection_refs` rows) runs its 8,000 deferred checks in 0.11–0.13 s with the indexes and 2.1–2.2 s without them (two runs each; the rest of the purge took 1.6–1.9 s either way). Without the indexes each check is a sequential scan of the table, so the time grows with records × projected Refs: at 120,000 `projection_refs` rows in one collection a reviewer measured 36–50 ms per check.

Migration 046 adds `retrieval_dispatch_checkpoint` and a nullable `last_error_at` on `projection_outbox` and `retrieval_outbox` (with `retrieval_outbox`'s update guard allowing it as a delivery column); it runs under the migrator's five-second lock wait (adding each column waits for record writers, outbox workers and space purges already running, then takes a moment). It locks `projection_outbox` before `retrieval_outbox`, the order space purges and status reads use, so a purge in flight finishes and the step then applies; a writer holding them the other way round can still make PostgreSQL abort the step as a deadlock, and that, like a lock wait past five seconds, rolls the step back and fails with retry guidance. The migrator commits 045 before 046, so a purge started while 045 applies finishes rather than deadlocking with 046's change to the record outbox. Migration 047 builds the `retrieval_outbox_age` index over pending evidence work with `CREATE INDEX CONCURRENTLY`, on its own outside any transaction (still under the migrator's session lock), so evidence writers, retrieval workers and purges keep running while it scans a populated outbox; it waits for transactions already writing the outbox and for older snapshots, without blocking them. An interrupted build leaves an invalid index and 047 unrecorded; the next run drops it concurrently, builds it again and records 047 only once the index is valid. Status works without the index meanwhile, reading the backlog instead of one row. 045 is unchanged, so a cell that applied it upgrades without checksum drift.

Run `pnpm db:grant-retrieval` after migration 046 and after every restore. It grants the cell operational role `SELECT` on every retrieval table (space deletion reads the space-scoped ones to prove erasure); `INSERT` on `retrieval_policies` (its trigger maintains `retrieval_collection_heads`, which the role cannot write); `INSERT, UPDATE` on `projection_generations` and `projection_refs`; `INSERT` on `projection_deletion_receipts`; `INSERT, DELETE` on `lexical_chunks`, `vector_chunks` and `embedding_checkpoints`; `UPDATE` on `retrieval_outbox`; `SELECT, UPDATE` on `retrieval_dispatch_checkpoint`; and `EXECUTE` on `public.vector(public.vector, integer, boolean)` and `public.cosine_distance(public.vector, public.vector)`. The cast is needed because an HNSW index casts each inserted embedding to its dimension and PostgreSQL checks `EXECUTE` on that cast function for the inserting role; search ranks vector candidates with the cosine distance operator `<=>`, whose backing function needs the same grant (without it every vector query fails with `permission denied for function cosine_distance` and search degrades to lexical with `VECTOR_QUERY_FAILED`); the [regional runbook](regional-topology.md) revokes `PUBLIC` execution of public-schema routines, and without the cast grant a vector insert fails with `permission denied for function vector`. Both grants are for the cell operational role only, never a control, settings or disposable probe role; the runbook's shared recipe still grants only `l2_distance`. No grant allows `DELETE` or `TRUNCATE` of policies, generations, projected Refs, receipts or work: removal stays with the scoped purge routine. Policy validation runs in triggers, so writers need no other routine grant.

## Indexing worker (STA-45)

The jobs Worker chunks, embeds and projects configured content into every generation of a collection that is not retired (`building`, `verifying` and `active`). Projections stay derived data: exact record, source and claim reads and writes never call the embedder or wait for projection work, and nothing here returns projection content to a caller.

### Embedding port and registry

`@stateplane/retrieval` defines the port. An `Embedder` has a profile (embedder, model, model version, dimensions, processing region, relative quality, relative cost, `maxBatch` and `maxInputCodePoints`) and `embed(texts, signal)`, an external call that returns one vector per input. A provider that cannot be reached, is overloaded or gives up on its signal throws `EmbedderUnavailableError` (code `EMBEDDER_UNAVAILABLE`); anything else it throws, and an answer that is not one finite, nonzero vector of its dimensions per input (`EmbeddingRejectedError`), is the input's. `EmbeddingRegistry` holds the configured embedders, one per identity and region, each as a frozen snapshot of its validated profile with its `embed`, and returns those snapshots, so changing a profile after registration changes no selection, region check, limit or recorded identity. Before every call the snapshot's `embed` rereads the adapter's own profile and, unless it can be read and still matches the snapshot in every field (a mutated or replaced profile, or a profile, field getter or proxy that throws, does not), refuses with a rejected `EmbedderUnavailableError` without calling the adapter, which the worker settles as an outage, uncounted, so an adapter never runs under an identity, region or limit other than the one authorized:

- `select({ regions, dimensions, inputCodePoints, minQuality })` chooses an embedder for a new generation (STA-48 starts generations): only in a region the policy allows, with a dimension the cell has an index strategy for, accepting the chunker's input and of at least the required quality; then the lowest cost, the highest quality, the earliest allowed region and the name.
- `resolve(identity, regions, inputCodePoints)` returns the embedder with exactly a generation's identity in the first allowed region that has one. The worker uses only this, so a generation's vectors always come from its own model and version.

`DeterministicEmbedder` is a local test embedder: signed feature hashing of lowercased word tokens, L2-normalized (texts sharing words are closer). It calls nothing external and is not a semantic model.

The jobs Worker's registry is empty: no provider's processing region has been qualified for a cell (a regional label is not proof of residency). Generations without vectors therefore apply, and each vector generation keeps its previous state, its work stays due and status reports `degraded` with `embedderAvailable: false`, until a qualified provider is configured ([below](#prepare-and-apply)).

### Chunker

Only configured content is chunked, indexed or embedded: a record's policy-listed fields (JSON Pointers, in policy order) whose values are strings, a source's latest extraction content when `source_content` is on, and a claim revision's statement when `claim_statements` is on. Other fields, values of other types, unlisted kinds and everything else about a Ref are never read into a chunk. A text is split by code points into chunks of at most 1,000 code points, cutting after the last whitespace in a chunk's second half when there is one, with 100 code points of overlap; whitespace-only chunks are dropped. A record string may hold U+0000 or an unpaired surrogate, which PostgreSQL text cannot store; chunk content holds U+FFFD in its place, one code point for one, so offsets stay those of the authoritative text and such a record projects instead of failing. `chunk_index` numbers a Ref's chunks across its fields, so lexical and vector chunks of one revision share indexes and offsets. The vector side stores the SHA-256 of each chunk's text (`content_sha256`).

### Prepare and apply

Each delivery projects one Ref's authoritative target: a revision (with, for a source, its extraction version) and its content, or its deletion.

Every retrieval write transaction (preparation's plan and checkpoint saves, an evidence item's apply, and a record's fallback apply) first share locks the Ref's space and collection rows through its commit and proceeds only while the space is `active` or `readOnly`, the collection is not deleted and the space is still at the placement generation the work runs under (a record delivery's, or the one an evidence item read when it started), as completion's scope check does. Suspension, deletion, erasure and a placement fence update those rows, so each either commits before such a transaction, which then sees it and writes nothing, or waits for its commit; erasure locks the space first, so its purge never meets a checkpoint or Ref written after it began.

1. **Prepare**, outside any SQL transaction. In short transactions of its own it reads the collection's generations and, for each vector generation, records the Ref in the generation at its target revision when the generation has never projected it (so checkpoints can reference it), drops checkpoints whose region the policies no longer allow, and finds the chunks that still need an embedding. Embeddings of the same text already in the generation, from an earlier revision's vector chunks or checkpoints, are reused, so a claim review (a new revision with the same statement) calls no embedder. The rest are embedded in batches of the embedder's `maxBatch`, each batch saved as `embedding_checkpoints` in its own transaction; no connection is held while the embedder runs. A generation that has deleted the Ref, holds a newer revision or already holds this one completely is skipped. Content is sent only to an embedder whose region both the generation's policy and the collection's current policy allow; when none is configured, that generation's preparation fails with `EMBEDDER_UNAVAILABLE` before any call. Before every embedding call, each retry included, a short transaction rechecks that the space and collection are open, the generation is not retired and both policies still allow the embedder's region; a suspension, deletion or narrower policy committed since stops that generation's preparation (`PROJECTION_INCOMPLETE`) before more content leaves. A call already in flight when a narrower policy commits still completes, and the storage trigger then refuses its checkpoints; that refusal is reported the same way, so the work runs again at once under the new policy rather than failing. A checkpoint is saved only while the scope is open, the generation's Ref is live and not past the target (share locked, so an apply waits or is seen) and the target is not yet complete there, so a late preparation leaves nothing behind. A generation that cannot be prepared does not stop the others: preparation tries every vector generation and then reports the first error that is the target's own, else the first outage. Each vector generation with work gets an equal share of the preparation budget's remaining time (the last one all of it), so an embedder that fails, hangs or ignores its signal cannot spend another generation's time. Each generation's cut is judged by its own progress, whatever its siblings saved: one cut by its share before saving anything counts as an outage (the work waits with outage backoff instead of rerunning at once), and later items in the same evidence step skip that embedder (as they skip one that failed) without calling it. A healthy embedder whose single call outlasts its share is treated the same way while another vector generation has work: the shares are initial protective bounds, not measured provider latency.
2. **Apply**, inside the delivery's fenced transaction (with a 1-second lock wait), for each generation that is not retired, after share locking it so retirement waits: a generation that has deleted the Ref or holds a newer revision (or extraction) is left alone. A deletion removes the Ref's lexical and vector chunks and checkpoints, marks its `projection_refs` row deleted at the deletion's revision (inserting a deleted row for a Ref the generation never projected, which keeps a later stale delivery out) and records a deletion receipt. A live target replaces the Ref's chunks with its configured chunks: lexical chunks when the policy enables them, vector chunks only from checkpoints of exactly that revision, chunk and text digest in an allowed region. A vector generation missing any of them (an outage, no configured embedder, interrupted preparation) keeps its chunks, lexical side included, so a Ref in a generation is always at one revision; the other generations apply, and the work stays due for it (below). A policy narrowing that commits between the region read and the insert is refused by the storage trigger and reported as `PROJECTION_INCOMPLETE`: the apply rolls back and runs again, uncounted. Applied checkpoints, and older ones, are then removed; a generation already at or past the target only has its checkpoints up to its own position removed, so a superseded or late preparation leaves none behind once any later delivery of the Ref applies. Every applied position leaves the Ref's `projection_refs` row at it, with no chunks when the generation's policy configures no content the target has (a record without its configured fields, a whitespace-only extraction), so a preparation of an older position that starts later finds the generation past it and neither records the Ref nor saves a checkpoint. A Ref's first row is inserted only if absent and then locked: concurrent first applies of one Ref (overlapping ticks, or a record's fallback apply and completion) serialize on it, and the later one compares forward like any other instead of failing on the key. A generation whose policy configures nothing for the Ref's kind is not touched.
3. **Authority fence**, last in the same transaction: the Ref's authoritative rows are locked against their writers and reread. A record's row is share locked; a claim's `entity_refs` row is share locked (its revisions and deletion update it); a source's extraction lock is taken shared and its `entity_refs` row share locked (extractions and the source's deletion hold that lock exclusively). If authority no longer holds the applied target, the transaction rolls back and the work runs again with fresh state, so a revision, extraction or deletion that commits between the item's reread and its commit is never projected over. When no live generation configures the Ref's kind, apply writes nothing and the fence is skipped, so its writers never wait for it. Taken just before commit, the locks make a writer wait only for that commit, never for an apply or an embedder; a writer already holding its lock makes the fence wait at most the 1-second lock wait, after which the work is released as an outage.

Ordering and duplicates therefore cannot activate stale content in any generation: a projected Ref only moves forward, a deleted one stays deleted, and the storage's foreign keys and order check (above) refuse anything else even if a caller bypassed the worker.

**Records** use the record outbox ([durable outbox](durable-outbox.md)): its queue consumer calls `outbox.process(hint, new RecordRetrievalProjector(pool))`. The outbox already calls `apply` only for the record's latest committed revision, moves the per-ref head forward only and fences lease, scope and placement; prepare runs between its start and completion transactions. When some generation cannot be prepared, the generations that do not need it apply at once in a transaction of the projector's own, under completion's fences held through its commit (the scope fence above with the delivery's placement, and the authority fence) and within at most 3 s and the delivery's own budget, and the error is then thrown. The projector bounds itself by the delivery's deadline, which the outbox passes to `prepare`: preparation gets at most half the time the delivery has left and its grace at most an eighth of that, the fallback apply ends at least 250 ms (at most an eighth of the time left) before the delivery's deadline, and a backstop at that point ends anything still running as an outage, so even a short `processingMs` never turns an embedder outage into the delivery's counted failure (when the scope has closed, `prepare` returns and completion releases the delivery): an outage or interrupted preparation releases the lease without spending the failure budget and records `last_error`; any other error counts toward the dead letter, as for every projector. The delivery therefore stays due, and the record's projection head does not move, until every generation has the revision; later attempts find the applied generations complete and leave them alone. A record changed after completion read it fails the fence with `PROJECTION_INCOMPLETE` and is released uncounted; the outbox then supersedes it.

**Sources and claims** use `retrieval_outbox`, through `PostgresRetrievalWorker.step`. A claim leases due items by moving `available_at` 60 seconds ahead; that exact timestamp is the lease. Starting an item increments its `attempts` and renews the lease, so `attempts` counts started attempts only and backoff grows with them (a start whose transaction rolls back spends nothing and is released under the claim's lease with its error recorded); only the current lease, while it lasts, can start, complete or release an item. Items a step has no time left to start (it starts one only with at least 1 s of its budget left) are made due again at once, with no attempt spent, the cursor below moves back to the last pair whose item started (or where the claim found it, unless another claim has moved it since), so pairs whose claimed items never started keep their turn, and the step ends. Space/collection pairs with pending work take turns as a ring: each claim walks up to 100 of them, starting after the last pair a claim served (a cell-wide cursor, the single row of `retrieval_dispatch_checkpoint`, migration 046, kept across steps, ticks and workers and naming only a position) and wrapping around, skipping spaces that are not `active` or `readOnly` and deleted collections (their work stays pending, unclaimed and uncounted), and takes up to 2 due items from each and 8 in all, serving them in ring order. A due pair is therefore served within as many claims as there are due pairs ahead of it, however long their backlogs. A step ends when a claim's walk covered the whole ring, or 1,000 walked pairs, without finding anything due. Each item reads its Ref's **current** authoritative state fresh (the `entity_refs` revision and tombstone, the source's latest extraction or the claim's current revision), prepares it, and then applies in one transaction, within the item's budget, that takes the scope fence, locks the item's lease and rereads the authoritative state. If the space closed, its placement generation changed (a placement fence) or the Ref changed since it was read, or the authority fence finds it changed before commit, the item is released at once, uncounted, to run again with fresh state; its next attempt runs under the new placement, as the record outbox requeues a latest revision under it (the generation recorded in the work row is the one at enqueue, kept for provenance, since every item projects current authority); otherwise the target is applied. With every generation applied the item becomes `delivered`; with a vector generation left behind, the others' apply commits and the item stays pending, in the same transaction, with the backoff and `last_error` of what stopped that generation. Because every item projects the Ref's current state, a duplicate, late or reordered item applies nothing older. An expired lease cannot complete (`lost`).

### Failures, outages and status

| Situation | Effect |
| --- | --- |
| Embedder unreachable, overloaded or not configured in an allowed region | Each batch is tried three times (waiting 250 ms, then 1 s, within the budget). Generations that do not need that embedder apply; the item is then released with backoff (from 5 s, doubling, at most 5 minutes) and `last_error` `EmbedderUnavailableError EMBEDDER_UNAVAILABLE`. Later items in the same step skip that embedder. Record work is released uncounted by the outbox. |
| Preparation runs out of its budget | It stops starting batches after 15 s (for a record, after half the delivery's time left; for an evidence item, after half the item's budget, which is at most 20 s and less at the end of a step), gets up to 1 s (at most a quarter of the item's budget) to save the batch it has, and the item is released with no error and due at once if it saved checkpoints (`PROJECTION_INCOMPLETE`; the next attempt continues from them), or as an outage if it saved none. Preparation and its grace therefore end before the item's own budget; if the caller's budget ends first anyway, the outcome is the same, never the item's failure. |
| Processing policy narrowed during preparation or apply | That generation stops before any further call to the removed region; the work runs again at once with no error, under the new policy (`PROJECTION_INCOMPLETE`). |
| Authority changed before commit | Rolled back and released due at once, with no error. |
| Space suspended or being deleted, or collection deleted, during preparation | No further embedding call and no checkpoint; the item is released with no error and waits unclaimed until the space reopens. A record delivery is released by its completion. |
| Placement fence during preparation | The same: no further call and no checkpoint. An evidence item is released uncounted and its next attempt runs under the new placement; a record delivery is released by its completion and requeued by the fence's reconciliation. |
| A transaction still running when its budget ends | Every worker transaction is bounded: preparation's (generation reads, plans, admission checks and checkpoint saves) by its budget and grace, ending at once when the caller's budget does, so a batch received after the grace is never saved; an item's start and apply by the item's budget; a claim by the step's; and settling or releasing what the step holds by 1 s, ending at most 1 s after the step's budget. A bounded transaction checks its session out within its budget (a session that arrives later goes back unused, and BEGIN is not sent), sends no statement, from BEGIN to COMMIT or ROLLBACK, once its deadline passes or its signal aborts, and bounds each of the body's statements by the time it has left (`statement_timeout`, lowered whenever the time left falls more than 100 ms below it). At the deadline or an abort it stops waiting for the statement in flight (BEGIN, the setup, COMMIT and ROLLBACK included), cancels it from another session (only while that backend is still in the same transaction; the cancellation, checkout included, gives up within 1 s and discards its own session if unanswered, so on a one-session pool it holds the session no longer) and discards its session, so its locks go at once and a one-session pool is free again; a COMMIT cut short that way has an unknown outcome. An apply cut short is released with outage backoff and `last_error` `DeadlineExceededError`; a start cut short is released under the claim's lease the same way, with no attempt spent; a claim cut short ends the step, and leases a cut-short claim's COMMIT may have taken expire unstarted. A record's fallback apply whose 3 s or delivery budget ends gives way the same way, commits nothing, and the delivery's own outage is reported. |
| Lock wait, serialization failure, lost session | Released with outage backoff and its code as `last_error`. |
| Any other error, such as an embedder rejecting an input or a statement timeout | Retried with backoff from 5 s doubling to one hour and its bounded diagnostic in `last_error` (name and code only for coded errors, as for the record outbox; at most 1,024 UTF-8 bytes, cut between characters). Nothing an embedder throws is stored: a provider message can quote its input, so the port replaces every error from `embed` with `EmbedderUnavailableError` (an outage: `EmbedderUnavailableError` itself or a transient fault such as `ECONNRESET`) or `EmbedderFailedError` (anything else, counted as the input's), each with a fixed message and no cause. `retrieval_outbox` has no dead letter, so the item stays pending and reported as degraded. Generations that do not need what failed still apply. |
| Unknown COMMIT outcome | The lease is kept and expires; the item is then claimed again. |

`PostgresRetrievalWorker.status(spaceId, collectionId)` reports a collection's projection state: `degraded` when sampled record or evidence work has an error (including an uncounted outage release) or a vector generation has no configured embedder in a region its policies allow, `pending` when work is waiting, otherwise `current`; per queue, pending and degraded counts over at most the 500 oldest-due rows (for records also at most 500 failed rows; `capped` marks lower bounds) with the most recently recorded error among them (by `last_error_at`, migration 046, which every write of `last_error` sets and every clear empties, so a lease, a backoff or parking never changes which error is newest; an error recorded before 046 has no time and ranks oldest; ties go to the later event or job; for records the newer of the two samples' newest errors; failed rows are sampled in event order, so the same rows on every call); the oldest pending evidence item over all of the collection's pending items (one row read through the pending enqueue-time index `retrieval_outbox_age`, migration 047; PostgreSQL picks that index from the table's statistics, so they must be current: autovacuum's analyze keeps them so, and a large burst of enqueues can be followed by `ANALYZE retrieval_outbox`, until which the lookup may sort the collection's pending rows instead), one backed off behind newer work included; and each generation's state, policy, projections, embedder identity and `embedderAvailable`. It is an operator and service read; transports come with STA-49.

### Bounds of the worker

Initial protective values, chosen for bounded statements and leases, not measured provider capacity or relevance (STA-49 evaluates chunking): chunks of 1,000 code points with 100 of overlap (at most 4,000 bytes, inside the 65,536-byte storage bound; an embedder must accept 1,000 code points); three tries per embedding batch; preparation budget 15 s plus a 1 s grace, and a record's fallback apply at most 3 s (inside the record outbox's 30 s processing budget); evidence items of at most 20 s under a 60 s lease, started only with at least 1 s of the step left, with preparation at most half and its grace at most a quarter of the item's budget; 1 s lock waits during apply; claims of up to 8 items, 2 per pair (never more than the claim's limit), walking 100 pairs, and a step stops after 1,000 walked pairs with nothing due; backoff caps of 5 minutes for outages and one hour for an item's own failures; status samples of 500 rows. The jobs Worker's once-a-minute tick runs `step` for up to 8 s after its other steps (15 + 7 + 10 + 5 + 5 s). The budgets sum to the 50 s tick budget and each is a hard end for its step's SQL and sends, so the retrieval step gets its whole 8 s on every tick, however busy the earlier steps are (it is skipped only with under 2 s of the tick left, more than an item's 1 s minimum plus its claim). With its 1 s cleanup and at most 5 s of teardown a tick ends by about 56 s, so ticks do not overlap and a tick holds only the one origin connection the topology allows it; were one to overrun anyway, leases and `SKIP LOCKED` keep overlapping ticks safe. A Ref's configured text is at most 1 MiB, so at most about 1,200 chunks; a larger one simply takes several attempts.

### Not covered here

Search ([below](#hybrid-search-sta-46)) only reads projections; there is no bundle, HTTP, CLI or MCP surface (STA-47, STA-49), and generations are not started, verified, activated, rebuilt or backfilled by the worker (STA-48): a generation started after content was written projects only content delivered after it starts until STA-48's rebuild. Policy narrowing, the space and collection lifecycle and the Ref's authoritative position (a newer revision or extraction, or a deletion, stops preparation of the superseded text with `PROJECTION_INCOMPLETE`) are checked before every embedding call, retries included, and again by the storage triggers when checkpoints and chunks are written, but an embedding call already in flight when a narrower policy commits still completes; its result is then refused and the work runs again under the new policy. No production embedding provider is configured.

## Hybrid search (STA-46)

`PostgresRetrievalSearch.search(actor, spaceId, request)` searches a space's projections and returns only hits that authority still holds and the caller may read now. It is an application service; HTTP, CLI and MCP transports come with STA-49. Exact reads and writes never call it, wait for it or depend on its embedder. `request` is `{ query, collections?, kinds?, limit? }`: a nonblank query of at most 1,000 code points and 4,000 bytes; up to 32 distinct collection IDs; any of `record`, `source` and `claim` (all by default); and a limit from 1 to 50 (10 by default). Anything else is `INVALID_ARGUMENT`.

### What is searched

The caller is admitted for the space as every service admits it (`PostgresSpaces.scope`: the space's placement, an owner session or a current agent key). A kind is readable in a collection with its read capability: records `records:read`, sources `sources:read`, claims `claims:read`; the owner reads every kind. Without `collections`, every live collection the caller can read for at least one requested kind is searched, at most 32 in ID order (`collectionsCapped` says when more exist); a listed collection that does not exist or is not readable for any requested kind is `NOT_FOUND`, and a key that can read none is `FORBIDDEN`. In each searched collection only its **active** generation is read, and only the kinds the caller asked for and may read there, so a kind the grant does not allow never becomes a candidate. A collection without an active generation is reported `unindexed`.

### Candidates and fusion

`@stateplane/retrieval` defines two candidate ports; `PostgresCandidates` implements both, each call in a short `REPEATABLE READ` transaction of its own, in which the search also reads each listed collection's projection state (step 5 below) from the very snapshot the candidates came from. Both read only chunks of what the caller could read when they run: in a live collection (one deleted since the plan contributes nothing), the Ref live at the chunk's revision (and, for a source, its latest extraction), and, for a claim, citing only live collections whose sources the caller may read (every live one for the owner; `CandidateScope.evidenceCollections`), the claim service's read rule. Deleted, superseded and hidden content therefore never becomes a candidate, so no count, rank or underfill reason discloses that it matched; the reread below still checks everything.

- **Lexical** (`LexicalCandidates.lexical`): chunks whose `tsvector` matches `websearch_to_tsquery` of the query under each generation's own text search configuration (qualified as `pg_catalog.<config>`, exactly as migration 045 builds the `tsvector`, so no `search_path` entry can substitute another configuration), ranked by `ts_rank_cd`, each Ref's best chunk once, best first, at most the overfetch bound over all collections. Only generations whose policy has lexical projection on are read.
- **Vector** (`VectorCandidates.nearest`): the query is embedded once per embedder identity and region, by the embedder with exactly the generation's identity in the first region both the generation's policy and the collection's current policy allow (`EmbeddingRegistry.resolve`). Immediately before each call, in a fresh read, the provider must still confirm the caller's credential and, for a key, the regional key and every grant the response relies on (step 3 below) must still be held, and all of them still unexpired once that read has committed, the call being the next step (on the monotonic clock, and on the wall clock for the provider's own stated expiry), or the search fails `FORBIDDEN` before the query leaves; the space must still be open at the admitted policy and placement, and each of the group's collections live at the planned active generation and policy version with the embedder's region allowed by both policies; a collection that fails this is searched lexically with `vectorError: POLICY_CHANGED`, and a group with none left makes no call. A narrowing committed during an earlier group's call therefore stops later groups, so the query never starts toward a region either policy excludes; one committed during the call itself cannot recall it, as for the worker. Each group gets one try (admission read and call), and all groups share one 2 s budget, so stalled providers in several groups never multiply the wait before the lexical list answers; the admission read, the provider's confirmation included, ends with that budget, its connection discarded if it is cut short, so a stalled read never holds a connection the lexical list needs, and a late one sends nothing and relabels nothing; a group the budget no longer reaches, or whose admission read or call it cuts short, is reported `EMBEDDER_UNAVAILABLE`. No call is waited for past the budget, even if the embedder ignores its signal. The nearest chunks by cosine distance are then read per generation through the dimension's HNSW partial index (with its cast and `dimensions` literal) or exactly for 3,072 dimensions, with `hnsw.ef_search` raised to the bound and pgvector 0.8's `hnsw.iterative_scan = strict_order`, so filtering to one space, collection, generation and kinds makes the index scan further instead of returning fewer rows.

The lists (lexical, then one per vector identity and selected processing region, so the same identity in two regions gives two lists with their own ranks) are deduplicated to each canonical Ref's best chunk and fused by reciprocal rank (`fuseRanks`, `k = 60` from Cormack, Clarke and Büttcher 2009, not tuned here): a Ref scores the sum of `1 / (60 + rank)` over the lists it is in, so one both lists rank well comes first; ties go to the better best rank, the earlier list, then the key. Each list fetches four times the limit, at least 20 and at most 200 (the overfetch bound), and at most that many fused Refs are considered. A vector list contains the nearest chunks whatever their similarity, so unrelated Refs can follow the matches; STA-49 evaluates relevance and may set a floor.

### Fresh reread and reauthorization

Every considered candidate is reread in a new transaction, after every candidate read and embedding call, so nothing a projection holds is returned on its own authority:

1. **Scope locks**, as `checkScope` takes them: the space row is share locked and must still be `active` or `readOnly` at the admitted policy version and placement generation (`SPACE_UNAVAILABLE`, or `FORBIDDEN` with "Policy or placement changed", otherwise). For the owner the searched collections are share locked; for a key its credential row (active, confirmed, not revoked, not expired; otherwise `FORBIDDEN`) and every grant it holds in the space, with the grant's live collection. A key revocation (which updates the space row), grant change, suspension, deletion or placement fence therefore either committed before, and is seen, or waits for the search to commit. Then the searched collections' **active generations** are share locked, so a cutover either committed before and is seen, or waits for the search to commit.
2. **One statement** rereads every citation from one snapshot: the record's row, or the source's or claim's `entity_refs` row (revision and tombstone), a source's latest extraction version, the cited range at the chunk's code-point offsets of the record field, extraction version or claim revision the chunk was built from (sliced with `substr` in SQL, which counts code points as the offsets do, after checking the text still reaches the range's end, so only the range leaves the database), a claim revision's review, attribution and evidence, and every collection any revision of the claim cites. Those cited collections are then share locked through commit, for the owner and keys alike, in one fixed order after the scope and generation locks (collections outside the search filter or cap included), as the claim service's evidence fence does: a collection deletion either committed before and is seen, or waits for the search to commit, and a cited collection's liveness is decided only from those locked rows. A record whose `jsonb` cannot hold its text (U+0000) has no `jsonb` value; its range is read from its canonical JSON at the candidate's revision, one record at a time and only for a candidate about to be returned.
3. For a key, under those locks, its current access is compared with the response's dependencies (one set, also used by the final check): every planned collection's read capability for each kind searched or reported there, including the 33rd readable collection whose existence makes the result `capped`, and (when claims are searched) `sources:read` on every collection the claim candidate filter treated as readable. When one is no longer held (a grant expired; a revocation or grant change also moves the space policy version), the search fails `FORBIDDEN` with no counts, because its candidates were read under the wider access and could include content written after the narrowing.
4. Every considered Ref is validated: a candidate from a collection the caller can no longer read for its kind is rejected as **unauthorized**; one whose Ref is missing or tombstoned as **deleted**; one whose generation is no longer the collection's active one (or whose policy version differs), or whose revision (or, for a source, latest extraction) moved past every chunk that found it, as **stale**; a claim citing a collection whose sources the caller cannot read (or a deleted one) as **unauthorized**, the claim read rule of the claim service. A citation is kept only if authority still holds exactly the revision it was built from. The surviving matches are then fused again (`fuseRanks` over each list with only the Refs whose citation from that list survived), so a rejected or superseded match neither ranks nor boosts a Ref: a Ref whose vector chunk was superseded between the vector and the lexical read is ranked, scored and cited by its lexical match alone, with no vector rank or embedder. The best `limit` of that fusion are the page; a canonical-JSON record's cited text is read only for a page hit, and one that no longer reaches the citation drops that citation and the page is fused again.
5. **Coverage** is the worst projection state observed, with the plan's own query (searched readable kinds, claims under the read rule), at the plan, in each candidate list's own snapshot, and again after every candidate read under the generation locks; one whose active generation or policy version moved since the plan is `pending`. A later `current` never overwrites an earlier `pending` or `degraded`, so work waiting when a list was read (a revision written before it, delivered before the reread) or a cutover is never reported `current` or `exhausted`.
6. **Final check**: the provider confirms the credential (an owner session or a key) and its expiry, then for a key one statement against one clock reading confirms the key and every dependency in step 3 plus `sources:read` on every collection a returned claim cites, whatever the page holds (also for an empty page), and the time left until the earliest of their expiries; the search takes the earliest of those and the provider credential's expiry, for sessions and keys alike (unbounded only when nothing it relies on expires; a provider that states no expiry, unlike AuthFn, bounds nothing). Share locks fence revocation and edits but not time, so COMMIT must be acknowledged within that time, measured from before each read (never shorter than the real interval), and before the provider credential's own expiry on the wall clock (so a clock step past it fails too); otherwise the search is `FORBIDDEN` although it committed, as a read changes nothing. No fixed margin is taken: an expiry after COMMIT answers.

### Result

| Field | Meaning |
| --- | --- |
| `results[]` | Hits in the order of the fusion over surviving matches: `ref` (space, collection, kind, ID), `revision` and `extractionVersion` authority holds, `score` (that fusion's), `citations` (one per chunk, each `matchedBy` naming every list whose best chunk for the Ref it is, lexical, vector or both, chunk index, field, code-point `start`/`end`, a source's `sourceStart`/`sourceEnd`, and the authoritative `text` there), `provenance` (generation, policy version, lexical and vector rank in the surviving lists, the embedder identity of a vector match, a claim's attribution and evidence), `review` (a claim revision's status, reviewer and time; null otherwise) and `freshness` (`verifiedAt`, the database time of the reread, and the collection's projection state) |
| `mode` | `hybrid` when some collection's vector list was used, otherwise `lexical` |
| `state` | `degraded` when a vector list was unavailable or a collection's projection work has failed; `pending` when work is waiting or a collection has no active generation; otherwise `current` |
| `collections[]` | Per searched collection: active generation, whether lexical was searched, `vector` (`used`, `disabled`, or `unavailable` with `vectorError`: `EMBEDDER_NOT_CONFIGURED`, `EMBEDDER_UNAVAILABLE`, `EMBEDDER_FAILED`, `VECTOR_QUERY_FAILED` (the vector query or the admission read failed within the budget) or `POLICY_CHANGED` (admission before the call found a narrower policy, a new active generation or a closed space)) and `projection` (`current`, `pending`, `degraded`, `unindexed`, read as the worker's status reads it, but only over work the caller could read: record work only when records are searched in the collection, source and claim work of searched kinds only, and claim work only for claims passing the claim read rule; live work, a failure or error among the 500 oldest-due such rows, or a failed record delivery. A key that may read only claims therefore sees no state from record writes or from claims hidden from it), and `unsearched`: the requested kinds the caller may read there that no candidate list covered, derived from what ran: every one when no list ran over the collection (no active generation, or no lexical side and no vector side used), otherwise those the active generation's policy does not project (records with no `record_fields`, sources without `source_content`, claims without `claim_statements`, every kind when the policy enables neither list) |
| `underfill` | Null when `limit` hits were returned; otherwise `returned`, `requested` and every reason that applies: `rejected` (candidates failed the reread), `bounded` (a list or the fused set reached the overfetch bound, so matches may exist beyond it), `capped` (readable collections beyond the 32 were not searched; for a key its grant on the first of them is a dependency, so it is never reported from a lapsed grant, while for the owner a deletion after the plan can only leave it conservatively set), `approximate` (a vector list over an HNSW-indexed dimension came back short of the bound; a filtered approximate scan can stop early, so that proves nothing; the exact 3,072-dimension scan's short list is complete), `exhausted` (only when none of `bounded`, `capped` and `approximate` applies and every searched collection is indexed, `current` when observed after the candidates, has an empty `unsearched` and, where vectors are on, had its vector side searched: every searched list returned all it had and nothing readable went unsearched), `degraded` (a vector side was unavailable), `unindexed`, `pending` (a collection's visible projection work is waiting or has failed, or its generation moved since the plan), `unprojected` (an active generation's policy projects a requested readable kind into no list, so those Refs were never searchable). Coverage is the policy's projected text: a record field outside `record_fields` is never search text, so `exhausted` never speaks for it |
| `candidates`, `rejected` | How many lexical and vector candidates were read and Refs considered; how many of the considered Refs (all of them, not only those up to the page) were rejected as deleted, stale or unauthorized. Each candidate statement filters to live content at the Ref's current position, under the access the plan read (the planned collections and kinds and, for claims, the collections whose sources were readable then). A key whose access narrowed before the reread fails `FORBIDDEN` instead of returning counts, so a rejection reflects only a change committed between a candidate read and the reread (a deletion, a newer revision or extraction, a cutover, or a claim-evidence change) about content the caller could read both when the candidates were read and at the reread |
| `complete` | Always `false`: a ranked page is never a complete answer, and no count, status or completeness follows from it |

The result is never padded: a rejected candidate is dropped, not replaced from beyond the bound. A vector or embedder outage, an unconfigured embedder (the jobs Worker's empty registry), or a failing vector query leaves the lexical list answering, with `mode: lexical`, `state: degraded` and the collection's `vectorError`; a collection whose policy has lexical projection off then returns nothing and says so.

### Bounds and limits

The numbers above (query size, limit, overfetch factor and range, 32 collections, the one 2 s budget for every embedding try) are initial protective bounds, not measured relevance or latency; STA-49 measures relevance, filtered recall and latency. The search runs short transactions (the plan, an admission read and a vector query per vector identity, the lexical candidates and the reread), each with the evidence services' 5 s statement and 2 s lock bounds, and holds no connection while the embedder runs. A lexical query ranks every matching chunk of the searched generations before taking the best, so its cost grows with the matches; the GIN index on `tsv` is not partitioned by space. HNSW recall under filtering is approximate even with the iterative scan (bounded by pgvector's `hnsw.max_scan_tuples`, 20,000 by default), which is why a result is never complete and a short HNSW vector list is reported `approximate`, never `exhausted`. Each candidate read checks the Ref's authority row (and a source's latest extraction, and a claim's cited collections) per matching chunk, so its cost also grows with the matches. The reread returns at most one chunk's range (1,000 code points, at most 4,000 bytes) per citation, at most 200 Refs with one citation per list each; a record held only as canonical JSON (at most 1 MiB) is read whole, one at a time, only while it is about to be returned, so at most `limit` times per list. `hnsw.iterative_scan` needs pgvector 0.8 or later; with an older extension the vector query fails and the search degrades to lexical.

## Context bundles (STA-47)

`PostgresContextBundles.bundle(actor, spaceId, request)` gives an agent cited excerpts for one explicit task or query, within a byte or token budget, framed as untrusted data. It is an application service over `PostgresRetrievalSearch`; HTTP, CLI and MCP come with STA-49. `request` is `{ task?, query?, budget: { bytes?, tokens? }, collections?, kinds?, limit? }`: at least one of `task` and `query`, each nonblank text within search's query bounds (1,000 code points, 4,000 bytes); `budget` with at least one integer limit from 1,024 to 262,144; and `collections`, `kinds` and `limit` exactly as search takes them (the limit, 10 by default, is the number of hits searched for). The query is searched, or the task when there is no query. Anything else is `INVALID_ARGUMENT`.

### Authority

A bundle is assembled only from the hits one `search` returned, so it has exactly search's [admission, reread and reauthorization](#fresh-reread-and-reauthorization): a deleted, stale (newer revision or extraction, retired generation), unauthorized (grant, kind or claim read rule) or revoked hit is never quoted; a revocation or grant lapse committed before the reread fails the bundle `FORBIDDEN`, and one committed during it waits for the search's commit. Assembly runs after that commit and the search's expiry check, reads nothing and calls nothing, so it cannot quote what the search did not authorize. Excerpt text is the authoritative text the reread returned, never projection content.

### Count, status and completeness

A bundle never answers how many, which state or whether a set is complete: those need exact authoritative reads (record get, query, count and exists; source, claim and link reads). That is guaranteed by the bundle's **output contract**, whatever its request asks: a bundle computes and returns no count, total, status (not even a cited claim's review status) or completeness. It holds only cited excerpts of authoritative text (below), has `complete: false`, no candidate, rejection or underfill counts, no `exhausted` signal and only the search's `mode` and `state` as `coverage`, and its frame is `trust="untrusted" complete="false"` with a notice that no count, status or completeness follows from the excerpts. This contract is how STA-47 meets STA-14's requirement that count, status and completeness requests are refused or answered from authoritative data, never from vectors (owner decision, 2026-11-04): no bundle answers one from vectors, whether or not its request is refused.

Refusal is **best-effort defense in depth** on top of that contract. A request whose task or query the classifier below recognizes as asking a count, status or completeness, or as outside the allowed forms, is refused `INVALID_ARGUMENT` before anything is admitted, searched or embedded, with a message naming exact reads and the allowed request forms; a refused task is refused whatever the query beside it. Whether free text asks for a status is a semantic question that no word list settles (any noun can carry one: `situation`, `standing`, `extent`), so the classifier is not the guarantee: a request it does not recognize is served and receives only the contract above. Structural refusal, from a closed request intent instead of free text, is deferred to STA-53.

`exactQuestion` in `@stateplane/retrieval` is that classifier. It **fails closed** on the structure it parses: a request is served only when every line, every clause and every coordinated subrequest of its task and its query is one of the allowed forms below, or a bare topic, and no deny rule matches it. An allowed opening never authorizes a later subrequest, and a topic cue is refused wherever it occurs. A nonblank task or query asks for nothing, and is refused as `unrecognized` before anything is searched or embedded, when no subrequest holds a letter or digit in any reading (punctuation, separators, symbols or a request prefix alone, such as `???`, `->` or `please`), or when any subrequest, or noun phrase continuing one, holds words but names nothing. A subrequest names something only when it holds a word that is not in `BUNDLE_FUNCTION_WORDS`, a closed set of English function words (articles and determiners, prepositions and particles, pronouns including `something`, `anything` and `everything`, conjunctions, question words, `not` and politeness words), not an auxiliary or modal, not the request verb opening it (`summarize`, `explain`, `describe`, `find`, `show`, `get`, `tell` and the like) and not a passage or summary word before a function word (`information on`, `passages about`, `an overview of`). So `tell me about`, `about`, `the`, `it`, `why`, `information on`, `something about`, `Summarize it`, `Explain this to me` and `Summarize everything` are refused, while `Tell me about refunds`, `Summarize the storm`, `Summarize the draft` (a request verb is framing only where it opens a subrequest), `why did the storm happen` and `notes` are served. The set is a closed grammatical class, so it is not the open status-noun list deferred to STA-53. A request prefix alone after a served request is politeness and stays served (`Summarize the storm, please`). Any other question (a clause with a question mark, or opening with a question word, an auxiliary or a modal) and any other instruction is refused as `unrecognized`, whatever it asks, since English has no end of ways to ask for a count, a status or a set; a deny rule names the refusal's kind (`count`, `status` or `completeness`) when one matches. It reads the text NFKC-normalized and lowercased, and also NFKD-decomposed with every combining mark removed and then lowercased (so `İS İT PAİD` and `ïs ïnvoïce païd` read as plain letters), each with every invisible character (`Default_Ignorable_Code_Point` and format controls such as zero-width spaces and joiners, soft hyphens and bidirectional controls) removed and, separately, read as a space; each of those also with a hyphen, underscore or dot between two letters (`how-many`, `list_all`, `is.it.paid`) read as a space; each line (`\n`, `\r`, vertical tab, form feed, U+0085, U+2028, U+2029) its own clause, with a list marker opening it (`-`, `*`, a bullet, `1.`, `2)`) removed, and, when there are several lines, also all lines read as one; separators (`/`, `|`, `\`, a bullet or middle dot, an en or em dash, `--`, a spaced `*`, `~`, `#`, `=`, `<`, `>`, `->`, `=>`, any arrow, a tab and an ideographic space) as clause boundaries, wherever they are, and `&` and `+` as `and`; curly apostrophes as straight ones, a clitic as its own word (`what's` as `what 's`) and whitespace collapsed. A request is refused when any reading is. It splits each reading into clauses at sentence punctuation, commas, brackets, quotes, spaced dashes, separators and line breaks, then each clause into conjuncts at the coordinators `and`, `or`, `nor`, `but`, `then`, `and then`, `and also`, `and or`, `plus`, `also`, `as well as`, `as well`, `after that`, `followed by` and `while`. A conjunct that opens with a question word, an auxiliary, a modal, a subject (`I`, `we`, `you`, `they`, `he`, `she`, `there`), an instruction or a request prefix is a subrequest of its own: it must be an allowed form or a topic by itself, and every deny rule, including those anchored at a clause's start, applies to it (`summarize the notes and list the suppliers`, `why did the storm hit and is invoice two paid`). A bare noun phrase continues the subrequest before it (`compare fog and tides`, `find notes about salt and pepper`, `why did the storm hit and the lantern fail`): the deny rules apply to the whole subrequest, the topic cues to the noun phrase, and only the subrequest's opening conjunct can make it an allowed form, so a later conjunct never completes one (`what did we finish and report on the storm` is refused). A question mark ends the clause's last subrequest. A **subordinate clause** is a clause of its own, so an allowed opening never authorizes it: a subordinator (`before`, `after`, `once`, `until`, `so`, `so that`, `when`, `because`, `since`, `unless`, `if`, `as soon as`, `in order to`, `by`, `without`, `instead of`, `although`, `as` and the like) before a subject pronoun, an auxiliary, a modal, an instruction verb or its `-ing` form (`summarize the notes before you list the suppliers`, `describe the storm so you can list the suppliers`, `... before enumerating the vendors`), and `to` before an instruction verb other than after a verb of wanting or trying (`summarize the notes to list the suppliers`; `I want to see notes` stays one request). A sequencing or `-ly` adverb inside a clause before a verb and its object is a boundary too (`harbor notes, quietly enumerate the towers`). It removes prefixes from the start of each conjunct, and a leading sequencing or `-ly` adverb (`first`, `next`, `then`, `finally`, `lastly`, `afterwards`, `in addition`, `meanwhile`, `again`, `simply`, `briefly`, `literally`, any other `-ly` word that is not a verb such as `apply` or `supply` and has no object after it), so `first list the suppliers` is classified as `list the suppliers` and `briefly summarize the storm` is served: politeness (`please`, `hey`, `so`, `can`/`could`/`would`/`will you`, `can`/`could`/`may I`, `I want to`, `I'd like to`), and a verb of telling or knowing (`tell me`, `let me know`, `remind me`, `know`, `find out`, `I wonder`, `I'm wondering`, `do you know`, `help me understand`) only before `about`, a question word or the clause's end, so `tell me the suppliers` keeps its verb. A request to be given something (`do you have`, `have you got`, `I need`, `I want`, `I'd like`, `I'm looking for`) is read as `get`.

The allowed forms, with every word the classifier accepts in each (the refusal message quotes `BUNDLE_REQUEST_FORMS`, a short summary of them with examples):

- **An instruction to explain**: a clause opening with `summarize` (or `summarise`), `describe`, `explain`, `outline`, `draft`, `compare`, `contrast`, `discuss`, `recap`, `clarify` or `paraphrase`. Such a conjunct always opens a subrequest of its own, so it is served after another request exactly as it is alone (`summarize the storm and describe current events`).
- **A request for passages**: `find`, `show`, `get`, `give`, `fetch`, `retrieve`, `pull up`, `bring up`, `look up`, `look for`, `search for`, `surface`, `provide`, `send`, `share`, `see`, `read` or `have` (a request to be given something, below, reads as `get`), optionally `me` or `us` and a determiner (`the`, `any`, `some`, `a`, `an`, a possessive, `those`, `these`, `relevant`, `recent`), up to three modifiers that are not a state, then a passage noun (`note`, `record`, `excerpt`, `passage`, `quote`, `quotation`, `mention`, `reference`, `discussion`, `document`, `material`, `log`, `account`, `detail` and their plurals, `context`, `background`, `information`, `info`, `documentation`, `docs`, `entry`, `entries`, `text`, `writing`) and `about`, `on`, `regarding`, `concerning`, `re`, `for`, `from`, `by`, `of`, `in`, `mentioning`, `covering`, `describing`, `discussing`, `that mentions`, `related to` or `relating to` something (`find the keeper notes on fog signals`).
- **A request for a summary**: the same verbs, optionally `brief`, `short`, `quick`, `high level`, `detailed`, `longer` or `concise`, before a `summary` (or `summaries`), `overview`, `description`, `explanation`, `explainer`, `outline`, `recap`, `background`, `context`, `digest`, `synopsis` or `account`, then `of`, `on`, `about`, `for`, `regarding`, `concerning` or `from` something (`give me an overview of the treaty`).
- **An allowed question**, anywhere in a clause: `why ...`; `how does`, `do` or `did ... work`, `happen`, `compare`, `differ`, `relate` and the like; `what did`, `does` or `do <someone> say`, `write`, `note`, `record`, `report`, `describe`, `mention`, `think`, `suggest`, `recommend`, `propose`, `argue`, `claim` or `explain about`, `regarding`, `concerning` or `on` something; `what <someone> said`, `wrote`, `noted` (and so on) `about` something; `what was said about`; `what happened during`, `in`, `at`, `on`, `before`, `after` or `throughout` something (not `what happened to`, a status); `who wrote`, `said`, `reviewed`, `authored`, `reported`, `recorded`, `noted`, `proposed`, `described`, `mentioned`, `suggested`, `raised`, `explained`, `argued` or `claimed` (positive: `who hasn't ...` is refused).
- **An embedded question** after other words: also `how` for manner (not `how many`, `much`, `far`, `often`, `long`, `soon`, `close`) and `what <someone> wrote` (`describe how the bridge was repaired`, `summarize what the keeper wrote`). Every question word in a clause (`what`, `which`, `who`, `whose`, `where`, `when`, `why`, `how`, `whether`, `if` and the `-ever` forms) must open an allowed question, so `summarize which invoices were paid` is refused.
- **A bare topic**: a subrequest with no question mark, not opening with a question word, an auxiliary, a modal, a subject or an instruction, and carrying no topic cue (below). A clause opens with an instruction when its first word is an allowed verb to explain or a known verb (`list`, `show`, `give`, `provide`, `furnish`, `compile` and about a hundred more), ends in `-ize`, `-ify` or `-yze`, or is followed by an object pronoun, a determiner or quantifier, a question word or a particle (`rattle off`, `dredge up the`); a first word that is a preposition, determiner, pronoun or conjunction, or one followed by `of` (`map of the harbor`), opens a topic. An unknown verb before a bare noun (`gimme suppliers`) is indistinguishable from a noun phrase and is served as one: a topic still gets only ranked excerpts, the deny rules and the topic cues.

Whether a subrequest holds a **second request** is decided by presence, wherever it occurs, not by its first words, in every form: an instruction verb (any known verb, the allowed ones included) after the subrequest's first word, unless a determiner or possessive before it makes it a noun (`the list`, `our update`), and before an object pronoun, a determiner, a quantifier, a question word, a particle or, for a verb asking for a set (`list`, `give`, `show`, `provide`, `name`, `count` and the like), a plural (`summarize the notes list the suppliers`, `harbor notes give me the suppliers`); before any question word, any word not known to be a preposition, conjunction, determiner, pronoun, participle or number, before a determiner or object pronoun, an unknown verb with its object (`harbor notes tenth procure the suppliers`); an auxiliary or a modal other than the one the subrequest's allowed question word opens, before that clause's finished verb (`summarize the notes is invoice two paid`, `explain why the gauge drifted is invoice two paid`); and a subject pronoun (`I`, `we`, `you`, `they`, `he`, `she`) other than right after an auxiliary, a modal or a question word (`why did we`, `how they`). A topic, bare or continuing, contains no instruction verb, auxiliary, modal or subject pronoun anywhere.

The deny rules apply to every clause, whatever its form, and name the kind:

- **Count**: `how many`, `how much`, `how often`, `count`, `number of`, `total`, `tally`, `sum`, `size of`, `headcount`, `census`, `quantity`, `amount of`, an amount owed, due, outstanding, remaining or left, and `owe`.
- **Existence**: a clause opening with `is`, `are`, `was` or `were` `there`; `exist`, `any more`, `any other`, `any remaining`, `none of`, `none left`, `the rest of`, `what else`, `who else` (completeness).
- **Status by name**: `status`, `state of`, `current state`, `progress`, `how far along`, `percent complete`, `what` or `which state`, `stage`, `phase`, `step`, `point` or `condition`; `how is ... going`, `coming along`, `doing` or `looking`; `where ... stand`, `where are we on`; `how close`; `any update`, `update on`, `latest on`; `when will`; `or not`; `yet to`; `still to`, `still needs to` or `still has to`; `awaiting`, `under review`, `on` or `off duty`, `in` or `out of stock`.
- **Any yes/no question**: a clause opening with an auxiliary (`am`, `is`, `are`, `was`, `were`, `has`, `have`, `had`, `did`, `does`, `do`, also with `n't`) or a modal (`will`, `would`, `can`, `could`, `should`, `shall`, `must`, `may`, `might`, `need`, also with `n't`), whatever its predicate. A clause that ends with a question mark and with a state or past participle, and does not open with `why`, `how`, `where`, `when` or `who`, is a yes/no question too (`invoice two paid?`).
- **Embedded questions**: any `whether` clause; `if` after a verb of asking or knowing (`know`, `check`, `see`, `ask`, `wonder`, `confirm`, `verify`, `determine`, `find out`, `sure`, `tell me`, `say`); `if` followed by a state; a clause opening with `if`.
- **A state reached**: `still` or `not yet` before a state, `not yet` before a participle, `yet` after a state, `marked` (`as`) before a state or participle.
- **Things selected by a state**: a state such as `unpaid`, `open`, `overdue`, `missing`, `overdrawn` or `unassigned` before a plural (`unpaid invoices`, `the open ones`).
- **Which things are in a state**: `which`, `what` or `whose`, then anywhere in the clause an auxiliary chain before a state or a past participle: a form of `be`, `get`, `remain` or `stay` (also `has been`, `had been`, `'s been`), possibly negated and with adverbs such as `still`, `currently`, `already`, `never`, `yet`, `finally` (`which invoices haven't been paid`, `which claims got approved`, `which tickets are currently open`, `what's been reconciled`), or a perfect `has`, `have` or `had` before one (`what has shipped`); `that` directly before such a chain (`the invoices that have been paid`); `who` before a passive chain or a negated perfect (`who has been paid`, `who hasn't signed`); and a clause opening with `which` or `what` and at most three words that ends with a state (`which tickets closed this week`).
- **Every member of a set**: `every`, `each`, `all` before a word (other than `about`), `complete`, `full`, `entire`, `whole`, `exhaustive` or `comprehensive` (up to two words) before `list`, `set`, `roster`, `inventory`, `register`, `directory`, `catalog`, `index` or `rundown`; `list`, `roster`, `inventory`, `register`, `directory`, `catalog` or `rundown` `of`; `listing`, `roster`, `inventory`, `directory`, `registry`, `checklist`; `exhaustive`, `completeness`, anything, something, nothing or everything `else`, `missing`, `left`, `remaining`, `outstanding`, `pending` or `undone`; a clause opening with `list`, `enumerate`, `itemize`, `catalog`, `tally` or `name` before a determiner (`name each supplier`); and `which`, `what` or `who` with `remain`, `remaining`, `left`, `missing` or `outstanding`.
- **A state after a plural**: in any subrequest but a why- or how-question, a plural followed by `not`, `never`, `yet` or `still` and a state or participle (`invoices not paid`, `orders never shipped`), or directly by a word only an adjective can be there (`un-...-ed`, `unpaid`, `undone`, `remaining`, `left`, `outstanding`, `missing`, `overdue`, `pending`, `due`, `incomplete`: `invoices unpaid`, `tasks left`).
- **Requests for a state**: a clause opening with `show`, `give`, `get`, `fetch`, `display`, `pull up`, `return`, `send`, `bring`, `find`, `retrieve` or `look up` (and `me` or `us` and a determiner) directly before a state (`show me the unpaid invoices`), or with `confirm`, `verify`, `check`, `make sure`, `ensure` or `double check` and later an auxiliary chain before a state or participle (`confirm the invoice was paid`).

**Topic cues** apply to a bare topic, to a request for passages (whose object is a topic) and to a noun phrase continuing any subrequest, wherever in it the cue occurs: a state or state-selecting word before or after its noun, negated or alone (`invoices not paid`, `invoice two: paid`, `paid or unpaid`, `done`), `remaining`, `left`, `missing` or `outstanding` (completeness), a trailing `all` or `list` (`supplier list`), and a closing past participle, possibly followed by `yet`, `already`, `today`, `this week` and the like (`the parts arrived yesterday`).

States include done, complete, finished, resolved and unresolved, open and closed, pending, blocked, approved, rejected, accepted, merged, shipped, paid and unpaid, overdue, outstanding, missing, remaining, settled, cancelled, late, active, ready, started, delivered, fixed, signed, submitted, received, verified, reviewed, expired, failed, succeeded, archived, deleted, published, live, current, valid, available, due and past due, in progress, on hold, on track, up to date and out of date. A past participle is any word ending in `-ed` or an irregular one (`done`, `paid`, `sent`, `made`, `built`, `left`, `written`, `lit` and so on).

Failing closed refuses some requests that ask no exact question: `Which keeper lit the lantern?`, `Who signed the harbor treaty?`, `How was the bridge repaired?`, `What is a tidal gauge?`, `What was decided about tides?`, `Does the keeper log describe the storm?`, relative clauses (`the keeper who lit the lantern`, `notes the keeper wrote`), `if` clauses, hyphenated phrasal compounds read as verb and particle (`follow-up notes`, `check-in procedures`), a plural selected by a state (`open questions`), a topic with a question mark, a topic carrying a state or remaining word that is not a status (`overdue invoice`, `open source notes`, `current events`, `left wing politics`, `notes left by the keeper`, `notes on the open sea crossing`), coordinations an allowed form cannot open alone (`How do tides and currents interact?`, `What did the keeper and the master say about tides?`, `Who wrote and reviewed the log?`, `Why was the bell rung and the lantern lit?`), a clause inside a topic or before a determiner (`it was all about the tides`, `notes we wrote about the storm`, `Summarize the notes the keeper wrote`, `Outline the steps the crew took during the storm`, `only the storm notes`), a later line opening with a verb and its object, since all lines are also read as one (`Summarize the storm` and `describe the flood` on two lines), an instruction verb with an object inside a question (`Why did the keeper find the leak`, `Explain how to fix the lantern`), and a subordinate clause with a subject (`Why was the lantern lit when it was dark?`, `Describe the storm so the crew can prepare`), and a list idiom whose conjunct names nothing (`Summarize the storms, floods and so on`, `notes about storms and the like`). Each has a served rephrasing as an allowed form or a topic (`notes about the keeper lighting the lantern`, `Describe how the bridge was repaired`, `Explain tidal gauges`, `notes written by the keeper`, `notes on the storm follow-up`, `Describe current events`, `Summarize the storm and describe the flood`, `How do tides interact with currents?`, `Who wrote the log, and who reviewed it?`, `notes about the tides`, `Why did the keeper look for the leak`, `Explain how the lantern is repaired`, `Why was the lantern lit at dusk?`, `Summarize the storms and floods`); a request to explain is not checked for topic cues, so `Summarize the overdue invoice` is served. A bare noun phrase ending in a question mark after an allowed form (`why was the lantern lit and harbor lantern?`) takes the form's question mark and is served; it asks nothing exact. A run-on with no punctuation, separator, line break, coordinator or subordinator between two requests is one subrequest, and the presence rules above refuse a known instruction verb, an auxiliary, a modal or a subject pronoun in it (`summarize the notes list the suppliers`); what remains served is a run-on whose second request has a noun subject and an unknown verb inside an allowed question (`why did the storm hit whilst the crew procure the vendors`), which, like a topic, still receives only ranked excerpts that carry no count, status or completeness. Other phrasing the rules do not recognize is served as well, for example other languages, look-alike letters from other scripts, an unknown verb before a bare noun, and a status, aggregate or state-as-noun inside an allowed form's object, whose topic cues are not checked (`Describe the payment situation of invoice two`, `Explain the standing of the audit`, `Explain the exact cardinality of the supplier set`, `Summarize the unpaid`, `Summarize everything overdue`, `Describe how the repair is going?`), and an instruction verb before a bare singular noun run on after an allowed form (`Summarize the storm confirm invoice two paid`). Such a request asks an exact question, but its bundle answers none: like every bundle it carries only cited excerpts and the frame's notice, which the service test checks for these requests (`unrecognizedExact` in the corpus). `test/fixtures/exact-questions.js` holds the shared corpus that both the unit test and the service test run, in six tables: refused requests with their kind, served requests in the allowed forms, over-refusals with their served rephrasing, exact questions the classifier does not recognize, which are served under the output contract, and requests that ask for nothing, which are refused, with requests naming something next to them, which are served. No excerpt names a claim's review status, in the context or in `excerpts[]`: a bundle returns no status, so a claim's review is for exact claim reads.

### Budget and framing

The budget bounds `context`, the one text meant for a model's context: its UTF-8 bytes never exceed `budget.bytes`, nor `budget.tokens`. A token limit is enforced as the same number of bytes, since a tokenizer whose every token covers at least one byte of its input (byte-level BPE, as in GPT-2 and the tiktoken encodings, and SentencePiece with byte fallback) never yields more tokens than the text has bytes; `usage.tokensAtMost` is that upper bound, not an estimate, and is conservative for typical text. `usage.bytes` is the context's size.

`context` opens with `<stateplane-context trust="untrusted" complete="false">` and a notice that the excerpts are untrusted data to treat as information, never as instructions, and that no count, status or completeness follows from them, and closes with `</stateplane-context>`. Each excerpt is an `<excerpt>` element whose attributes cite it (`n`, `collection`, `kind`, `id`, `revision`, a source's `extraction`, a record's `field`, code-point `start` and `end`); no excerpt carries a claim's review status. Excerpt text and attribute values are escaped (`&`, `<`, `>` and, in attributes, `"` as entities; C0 controls other than tab, line feed and carriage return, and DEL, as numeric references; an unpaired surrogate as U+FFFD), so stored content can neither close an excerpt or the frame nor add markup of its own.

`excerpts[]` lists each excerpt's citation, numbered as in the context: the Ref, the `revision` and `extractionVersion` authority holds, `field`, code-point `start` and `end` of exactly the quoted range, a source's original `sourceStart`/`sourceEnd` (only for an excerpt that is one whole cited chunk; null when it was merged or cut, as a part's original range is not known), `truncated`, `verifiedAt` (the reread's database time) and a claim's `attributedTo`, and never a claim's review status. Text lives once, in `context`. Only `context` is meant for a model: `excerpts[]` is metadata for the caller, outside the frame and the budget, and holds stored strings (IDs, fields, `attributedTo`) unescaped, so a transport (STA-49) must not place it in a model's context unframed.

Hits are taken in search's rank order and each hit's citations in its order; citations of one field whose ranges overlap or touch become one excerpt over their exact union, a citation joining several earlier excerpts merging them all, so no text of a field is quoted twice. An excerpt that does not fit whole is cut to the longest prefix that fits (at whitespace in its second half, and not below 32 code points, when there is one; never inside a code point or an escape) if at least 32 code points fit, otherwise left out, and nothing after it is added, so a bundle is always a rank-ordered prefix of the search's hits. `truncated` says an excerpt was cut or a cited range left out; with no hits the context is the frame alone.

### Bounds of bundles

The budget range (1,024 to 262,144) and the 32-code-point minimum cut are initial protective bounds, not measured settings; STA-49 evaluates them with relevance. The frame takes under 400 bytes, but each excerpt's element repeats its citation (collection, ID and field pointer, which the stores accept up to hundreds of bytes each), so with long identifiers the minimum budget may hold the frame alone, with no excerpt and `truncated` true; it never exceeds the budget. A bundle costs one search plus assembly linear in the quoted text.
