# STA-4 Railway regional topology and qualification

Status: definitions and a disposable qualification harness. No cell is operational until its connected provider and Cloudflare observations pass. The amended [STA-4 issue](https://linear.app/21n/issue/STA-4/03-provision-full-regional-cloudflare-topology-and-postgres) supersedes the former AWS RDS plan. Skillplane's control/cell split is retained; its historical region choices are not deployment requirements.

## Provider, regions and budget (2026-09-28)

[Railway's current region list](https://docs.railway.com/deployments/regions) maps `asia-southeast1-eqsg3a` to Singapore, `us-east4-eqdc4a` to Virginia and `europe-west4-drams3a` to Amsterdam. The provider region must be read back from **both** the deployed service instance and attached volume; a logical cell ID or DNS name is insufficient. Railway says moving a volume between regions entails migration and downtime. Recheck availability before provisioning.

| Environment | Control | Cells | PostgreSQL services |
| --- | --- | --- | ---: |
| Development | Virginia | `ap-southeast` Singapore, `us-east` Virginia, `eu-west` Amsterdam | 4 |
| Production | Virginia | `ap-southeast` Singapore, `us-east` Virginia | 3 |

PostgreSQL grants routine `EXECUTE` to `PUBLIC` by default. Prepare grants separately in **both control databases, all five cell databases, and every separately created disposable database** after installing pgvector and before protected SQL, storage readback, DDL or Preview verification. Connect as the database administrator or extension/routine owner authorized to revoke and grant these privileges; a Worker or settings login cannot prepare them. Repeat the recipe after restore or retry. Use the actual role for that database. `psql -v` role arguments are visible in process listings and shell history: role names are identifiers, not credentials. Supply database passwords through protected files or secret environment bindings, never command arguments. Keep each database's role and URL in its separately protected inventory.

Run this block in each **operational control or cell database** with `psql -v target_role=<that-database-operational-role>`:

<!-- pgvector-role-grants -->
```sql
REVOKE EXECUTE ON ALL ROUTINES IN SCHEMA public FROM PUBLIC;
GRANT EXECUTE ON FUNCTION public.l2_distance(public.vector, public.vector)
  TO :"target_role";
```

Run the same block with `target_role=<that-database-probe-role>` in each **disposable database**, which has its own extension and grantor. Do not name a probe role in an operational database. Apply equivalent `PUBLIC` revocation in every other user schema. For each role that can create routines, its owner or an administrator must run `ALTER DEFAULT PRIVILEGES FOR ROLE <creator> REVOKE EXECUTE ON ROUTINES FROM PUBLIC` **without** `IN SCHEMA`; a schema-specific revoke does not remove PostgreSQL's global default `PUBLIC` grant. Explicitly approve any other application routine grants only for their intended operational roles. The distance grant is limited to the pgvector backing function. The shared admission checks deny settings logins all effective user-schema routine execution; the disposable Worker also denies unrelated routine and sequence access while requiring the distance grant. Verify effective grants after restoration and before every qualification retry, including the disposable role's distance query before Preview DDL.

Each control/cell is a separate Railway PostgreSQL service and volume with its own database, role, Hyperdrive config and protected credentials. Use separate Railway projects and Cloudflare accounts or equivalently isolated provider environments with distinct credentials; the private inventory records the project/environment IDs. Before promotion, compare both inventories and reject reused project, environment, service, volume or Hyperdrive IDs. The control database holds only identity and placement metadata; STA-5 owns the schema, routing and authorization. No production business content belongs in development.

Every protected operational resource and disposable target inventory also requires `volumeMountPath`. Read back `volumeInstance.mountPath` through the connected Railway account, then use a separate protected settings-only SQL login to read the running server's `current_setting('data_directory')` over verified TLS. The data directory must equal the mount or be a child of it. [PostgreSQL documents `data_directory` as the running storage location](https://www.postgresql.org/docs/current/runtime-config-file-locations.html); it can override `PGDATA`. Create a distinct login for each resource with only `CONNECT` and direct [`pg_read_all_settings`](https://www.postgresql.org/docs/current/predefined-roles.html) membership. It must not be the Worker/Hyperdrive role, own or access application objects (including large objects), create databases or schemas, hold elevated attributes, or belong to another role. The verifier rejects effective large-object `SELECT`/`UPDATE`, user-object ownership by the login or inherited settings role, `lo_compat_privileges` mode, and explicit parameter `SET`/`ALTER SYSTEM` grants before storage readback; operational and disposable role admission also rejects effective parameter administration. It also rejects non-default tablespaces. These checks do not resolve a `pg_wal` symlink or prove its container path; record that limit rather than claiming path-level proof. Require populated provider backup readback and a timed PITR restore with recovered-row comparison to prove recoverability. Repeat the provider, SQL and restore proofs after restore, redeployment and every retry. A volume ID, mount path or image default alone does not establish durable database writes.

Use a digest-approved Postgres image with pgvector available and Railway PITR support. [Railway's default Postgres template does not promise extensions](https://docs.railway.com/databases/postgresql); the image digest must be independently approved and `CREATE EXTENSION vector` plus a vector query must pass on a disposable copy before any environment is accepted. The private inventory records the expected image reference, approved immutable digest and database role for each resource; the verifier matches the image against the Railway service instance, then queries the expected database and role through its TCP proxy with the exact uploaded CA, hostname verification, PostgreSQL version and pgvector distance check. This local SQL proof still needs a real Cloudflare Worker transaction through Hyperdrive `verify-full`. A private-network or unverified TLS variant requires a separate proven path. Keep database URLs, passwords, deployment tokens and CA private material in provider/CI secrets, never in manifests, inventories, logs or PRs.

**Capacity assumption, pending measurement:** seven small services at 0.25 vCPU, 0.5 GiB RAM and 1 GiB volume each would cost about USD 71.05 per 730-hour month at [Railway's published resource rates](https://docs.railway.com/pricing) (7 × (0.25 × $20 + 0.5 × $10 + 1 × $0.15)). This is a planning envelope, not a reservation or quote. Plan subscription/minimums, actual CPU/RAM use, extra volume and snapshot blocks, PITR bucket storage, TCP proxy egress, Cloudflare requests/R2/Queues, logs and tax are outside it. Obtain a current project quote and spend cap before provisioning. One cache-disabled Hyperdrive pool per origin has `originConnectionLimit: 5`. The schema accepts only 5–20, the overlap between Cloudflare Free and Paid limits; it is a soft limit. Measure `max_connections`, active sessions under concurrent requests, reserve for migrations/PITR and p95 transaction timeouts. A load test must show acceptable headroom before increasing traffic.

[Railway volume backups](https://docs.railway.com/guides/postgres-backups-restores) are scheduled snapshots. Require a scheduled retention of at least one day in development and seven days in production, plus an unexpired backup with a provider snapshot ID and populated size readback. Railway's public `VolumeInstanceBackup` API has no status field, so an ID and timestamps alone cannot establish completion; the verifier also requires `externalId`, `usedMB`, `referencedMB` and `volumeInstanceSizeMB`. Treat this as snapshot readback, not proof that recovery works. Railway's daily schedule retains six days, so production needs an additional schedule with at least seven-day retention. [Railway PITR](https://docs.railway.com/volumes/point-in-time-recovery) uses WAL archives and creates a sibling service for recovery; enabling it requires a first base backup. The live verifier requests a recent restore estimate, but that is not a restore drill. The *planning alert target* is a latest restorable point within 30 minutes, with a recovery time target of 60 minutes. Neither is a promise until measured; record the provider's window, chosen restore timestamp, recovered rows, archive lag, restore duration and cutover duration. A successful logical dump restore is additional coverage, not a substitute for PITR.

## Placement and processing policy

| Data or work | Intended placement | Limit |
| --- | --- | --- |
| Authority SQL, native full-text, pgvector, receipts, outbox | One Railway service/volume in the cell's physical region | Read service and volume region through connected provider API; no cross-cell SQL binding. |
| Identity/placement directory | Environment's Virginia control service | IDs and destination metadata only; no records, originals, search text or business logs. |
| Originals and exports | Private R2 bucket per cell, `apac`/`enam`/`weur` location hint | A hint is not a jurisdiction guarantee; verify actual bucket location. |
| Projection jobs | Cell Queue and DLQ, consumed by its job Worker | Delivery is at least once and Queue processing location is not guaranteed. The scaffold consumer fails closed. |
| Embedding calls | Disabled pending STA-12 | No text sent to an embedding provider by this ticket. |
| Worker execution and logs | Smart placement near the origin, default Cloudflare processing | Placement and telemetry do not guarantee geographic confinement. Avoid contentful global logs. |
| Backups/PITR | Railway volume snapshots and WAL archive for each service | Confirm region/retention and test recovery; verify the archive bucket's actual location and access separately. |

Reject strict country or jurisdiction policies until SQL, R2, Queue, Worker, embedding, telemetry, backups and support access have independently verified controls. The manifest rejects unknown strict-residency fields. `ap-southeast` identifies Singapore affinity, not India; `eu-west` identifies Amsterdam affinity, not Ireland. Historical `in-south` references in generated Worker names, service bindings, R2/Queue names, database names and disposable probe IDs must be migrated together. Old resources must be inventoried and retired after cutover; do not silently relabel a live database.

## Provisioning, qualification and rollback

The disposable qualification login receives `CONNECT` on its database and `USAGE, CREATE` on its disposable `public` schema so it can create the probe table. It must have no database or other user-schema `CREATE` grant, access to another user table or sequence, EXECUTE on an unrelated routine, elevated role attributes, or membership in any other role. It must have EXECUTE on the exact pgvector distance function. The Preview Worker checks these effective grants and fails closed before DDL. The protected SQL verifier checks operational control/cell roles for safe login, no other-role membership, database `CONNECT`, public schema `USAGE`, no database or user-schema `CREATE` (including `public`), and no owned database object. Migrations must transfer table, view, sequence, function, type, partition and schema ownership to a separate migration role before admission; direct application table grants remain valid. The no-membership rule covers ordinary reader roles with `INHERIT FALSE` and `SET TRUE` as well as inherited and indirect grants. Both paths fail closed on missing or unavailable grants. Repeat checks after restore, redeployment and retries; a database owner or role with the expected name and an alternate reachable role does not qualify.

The load command redeploys and reads back the exact-head named Preview, then derives the probe URL from the returned HTTPS Preview origin plus `/qualify`; it sends no token to a caller-selected destination or redirect target and forwards interruption to Preview setup. An optional fourth argument asserts an expected probe URL and fails before the first request if the new deployment returns a different URL. Record the name and URL in its output for subsequent evidence. The authenticated `/qualify/reserve` endpoint first validates any preexisting probe relations against their exact owned base-table catalog shape, creates them if absent, and obtains a PostgreSQL-owned generation under a row lock and commits it only after a zero-residual read. `/qualify/start` accepts only that reserved generation; a delayed start from an older independent CLI cannot reopen a newer closed attempt. Each probe sends the generation, holds a shared row lock in a PostgreSQL transaction while its writer runs, and rejects a stale or closed attempt before mutation. The runner completes one serial probe, then ten requests in batches of two: at most four of the five origin connections can be held by its reader/writer pairs, leaving one available for progress. It requires at least five observed spare Postgres connections. The authenticated `/qualify/residual` endpoint takes an exclusive row lock, closes the attempt, and reads the table-wide residual count after the serial probe fails or all concurrent client responses settle. It waits for Worker probes that already hold the shared lock; probes arriving later fail admission. A replay reserves a new database generation, supersedes older delayed starts and refuses any residual rows before opening. A failed read, timeout, interrupted run, or incomplete close blocks qualification. The database fence is necessary because client cancellation does not prove Worker completion. Hyperdrive uses [transaction pooling](https://developers.cloudflare.com/hyperdrive/concepts/connection-pooling/) and [does not support advisory locks](https://developers.cloudflare.com/hyperdrive/reference/supported-databases-and-features/); the row locks are scoped to explicit transactions. The budget counts all server client backends across roles and databases and subtracts superuser/role-reserved slots. It samples connections at probe completion; also measure provider peak sessions and Hyperdrive origin pooling during the run because the sample may miss a short peak. Record latency/session measurements per physical region, TLS and redaction checks. Then perform a timed Railway PITR restore to a sibling disposable service, compare data at the chosen point, and test the cutover/rollback path.
