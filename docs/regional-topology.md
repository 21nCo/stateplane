# STA-4 regional topology and qualification

Status: deployment definitions and disposable qualification harness. No regional database, Worker, queue, or R2 bucket is declared operational solely by this document. The live inventory, transaction evidence and restoration measurements are required before promotion.

## Selection and pre-provision budget (2026-09-27)

Skillplane's checked-in production manifest has `in-south` and `us-east`; development also has `eu-west`. Its [deployment guide](https://github.com/21nCo/skillplane/blob/main/docs/operations/deployment.md) says the checked-in multi-cell renderer is a transition artifact rather than proof of a production multi-cell rollout. Stateplane models all five cell definitions independently. Each environment also has one minimal control database in `us-east-1` for identity and placement metadata; it must never hold records, original bytes, claims, search projections or application logs.

Selected managed provider: **Amazon RDS for PostgreSQL**. The physical database regions are Mumbai `ap-south-1`, N. Virginia `us-east-1`, and Ireland `eu-west-1`, according to [RDS regional availability](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.RegionsAndAvailabilityZones.html). [RDS extension listings](https://docs.aws.amazon.com/AmazonRDS/latest/PostgreSQLReleaseNotes/postgresql-extensions.html) include pgvector, but the exact engine/extension combination must pass `CREATE EXTENSION vector` and a vector query on the selected instances. [RDS automated backups](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.html) support point-in-time restore within the configured retention window. A restore drill, not availability in the product description, establishes recoverability.

Read-only AWS CLI checks on 2026-09-27 found PostgreSQL 17.6, `db.t4g.micro` and gp3 orderable in all three regions. The connected account has default VPCs in Mumbai and Ireland but none in N. Virginia; a dedicated N. Virginia VPC, subnets and DB subnet group are therefore a provisioning prerequisite. No Stateplane RDS instance was present in these three regions at that check.

The initial **qualification sizing assumption** is one Single-AZ `db.t4g.micro` with 20 GiB gp3 per database, seven RDS instances total: four development (control plus three cells), three production (control plus two cells). This is a small probe baseline, not measured serving capacity or a production launch size. `originConnectionLimit: 5` is a provisional cap on each of seven distinct cache-disabled Hyperdrive pools, so each RDS origin has at most one declared pool and five soft origin connections. Measure `max_connections`, active sessions, headroom for migrations and backup activity, p95 transaction duration and timeouts before retaining this setting or sizing up. RDS CPU credits, storage/IOPS above baseline, data transfer, R2, Queues, Worker requests, logs and backup excess are excluded from the estimate.

AWS Pricing API `AmazonRDS` On-Demand Single-AZ PostgreSQL and gp3 products, queried on 2026-09-27, returned these assumptions (USD, before discounts/tax):

| Region | Instances | `db.t4g.micro` / hour | gp3 / GiB-month | Baseline / 730-hour month |
| --- | ---: | ---: | ---: | ---: |
| `ap-south-1` | 2 | 0.021 | 0.131 | 35.90 |
| `us-east-1` | 4 | 0.016 | 0.115 | 55.92 |
| `eu-west-1` | 1 | 0.017 | 0.127 | 14.95 |
| **Total** | **7** | | | **106.77** |

The monthly calculation is `730 × instance count × hourly rate + 20 × instance count × gp3 rate`. [AWS pricing](https://aws.amazon.com/rds/postgresql/pricing/) bills instance time and storage separately, and backup excess and CPU credits may add cost. [Hyperdrive pricing](https://developers.cloudflare.com/hyperdrive/platform/pricing/) has plan-dependent limits but no separate origin-pool charge. A disposable external acceptance run creates only issue/head-named resources and deletes them; its actual bill is recorded separately. Promotion requires a current quote and an approved sustained budget. Target backup retention is 1 day in development and 7 days in production. The live gate requires `LatestRestorableTime` no more than 30 minutes old, independently of retention. [AWS documents five-minute RDS transaction-log uploads](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html); six upload intervals is a provisional fail-closed alert bound, not a measured recovery objective. No RPO or RTO is promised until a timed restore drill; record the measured latest restorable time, restore duration, DNS/Hyperdrive cutover time and acceptable loss window.

## Ownership and placement

| Data or work | Intended placement | Verified guarantee / gap |
| --- | --- | --- |
| Space authority, native full-text, pgvector, receipts, outbox | Cell's own RDS instance in mapped AWS region | SQL host and RDS instance region can be checked. Cross-region replicas are not configured. |
| Identity and placement directory | Environment's control RDS instance in `us-east-1` | Only IDs, destination cell, generation and minimum credential metadata; no business content. STA-5 owns schema and routing. |
| Original bytes and exports | Distinct private R2 bucket per cell: `in-south` → `apac`, `us-east` → `enam`, `eu-west` → `weur` creation hint | [R2 location hints](https://developers.cloudflare.com/r2/reference/data-location/) are hints, not strict jurisdiction controls. The manifest validator fixes this mapping; inventory must record actual bucket location. |
| Projection delivery | Distinct Queue and DLQ per cell, consumed by that cell's job Worker | [Queue delivery](https://developers.cloudflare.com/queues/reference/delivery-guarantees/) is at least once. No geographic processing guarantee is asserted. Inactive scaffold consumer fails and routes exhausted retries to DLQ. |
| Embedding calls | Disabled until STA-12 selects and verifies a per-cell processor | No text is sent to an embedding vendor by this ticket. |
| Worker execution and telemetry | Smart placement near data, default platform processing | [Smart Placement](https://developers.cloudflare.com/workers/configuration/smart-placement/) optimizes execution location; it does not lock execution to a jurisdiction. No contentful observability pipeline is configured here. |
| Backups and restore | RDS automated backups in the instance's AWS region, no cross-region copy configured | Live verification requires the declared retention and a valid `LatestRestorableTime` for control and every cell. A timed point-in-time restore still establishes actual recovery; backup location alone does not cover Worker, R2 or Queue processing. |

**Processing policy:** these cells support best-effort regional affinity with isolated SQL origins. Reject any strict in-country or strict-jurisdiction policy at admission until the SQL, R2, Queue, Worker, embedder, telemetry, backup and support-access paths have independently verified controls. The manifest rejects unknown strict-residency fields rather than silently accepting them. A cell label alone is not evidence of residency. The global control service does not route or authorize requests yet; STA-5 adds signed destination context and current policy checks.

## Provisioning and promotion

1. Verify the current commit and clean tree. Run `pnpm topology:validate`, `pnpm check`, and inspect the manifest in `deployment/topology.json`. Record an AWS Pricing Calculator quote, quotas, chosen engine/pgvector version, RDS `max_connections`, Cloudflare plan and connection headroom in the private change record. Do not place passwords, direct database URLs, access tokens or migration URLs in the manifest, generated Wrangler configs, PR or ledger.
2. In each declared AWS region, create a **separate** RDS PostgreSQL instance named `<prefix>-<cell>-db` (`<prefix>-control-db` for control). The validator applies [AWS's RDS instance-ID rule](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/CHAP_Limits.html) to every generated control and cell ID and to restore inventory: 1–63 characters, starting with a letter, with no trailing or consecutive hyphens. It also requires every normal ID to leave room for `-restore-` and an eight-character token, so an admitted topology always has at least one valid restore name for every database. Pass `--db-name` using the shared derivation in `scripts/topology.mjs`: replace hyphens in the environment prefix and cell ID with underscores, then join them with one underscore. The five cell names are `stateplane_dev_in_south`, `stateplane_dev_us_east`, `stateplane_dev_eu_west`, `stateplane_prod_in_south` and `stateplane_prod_us_east`; the control names in the manifest are `stateplane_control_dev` and `stateplane_control_prod`. The validator checks all seven against [RDS PostgreSQL's 63-character, letters/digits/underscores DBName rule](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_CreateDBInstance.Settings.html). Enable TLS and the declared backup retention. Enable RDS deletion protection on **every production instance, including control**, and verify that AWS reports it enabled; disposable development instances may omit it. Use a public RDS endpoint with ingress scoped to **port 5432 only** and **every current Cloudflare IPv4 CIDR**, plus every current IPv6 CIDR if RDS reports `NetworkType: DUAL`, from the [Cloudflare IP ranges API](https://developers.cloudflare.com/hyperdrive/configuration/firewall-and-networking-configuration/). The live verifier rejects incomplete coverage, unknown address families, every non-TCP or off-port rule, broader ranges, group/prefix-list sources, and unapproved IPv4/IPv6 sources across every attached security group. A temporary migration-client address must be removed before live verification; world-open IPv4/IPv6 and unknown CIDRs fail the gate. Store database and deployment credentials in protected provider/CI secrets, separated by environment and cell. Workers VPC with direct RDS TLS is currently unsupported: [Workers VPC does not accept a custom CA](https://developers.cloudflare.com/hyperdrive/configuration/connect-to-private-database-vpc/) and the RDS private CA cannot be verified through that route. A future trusted proxy or CA-capable path needs a separate real Worker-to-RDS proof before that network mode can be enabled.
3. For every database create exactly one Hyperdrive config, named `<prefix>-<cell>-authority`, using `--caching-disabled` and `--origin-connection-limit 5`. Read the instance's `CACertificateIdentifier` from RDS and run `node scripts/select-rds-ca.mjs <aws-region> <rds-instance-id> <private-single-root.pem>`. The script fetches that region's [AWS RDS bundle](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/UsingWithRDS.SSL.html), extracts exactly the root matching the instance's CA identifier, rejects missing/duplicate/expired roots, and writes a single PEM with mode 0600. The `us-east-1` and `eu-west-1` bundles contain multiple roots and **must not** be uploaded whole. Upload the selected PEM with `wrangler cert upload certificate-authority --ca-cert <private-single-root.pem> --name <environment>-<rds-instance-id>-<ca-identifier>`. Record its returned ID and SHA-256 fingerprint in the private change record, then create Hyperdrive with **both** `--ca-certificate-id <uploaded-id>` and `--sslmode verify-full`; an absent or malformed CA ID fails live topology verification. Its credentials belong in Hyperdrive, not a Worker variable. [Cloudflare's Hyperdrive certificate guide](https://developers.cloudflare.com/hyperdrive/configuration/tls-ssl-certificates-for-hyperdrive/) requires one regional root. Do not pass a password on a shared command line or save it in shell history. Run `CLOUDFLARE_ACCOUNT_ID=<account-id> CLOUDFLARE_API_TOKEN=<protected-token> node scripts/verify-topology.mjs <environment> <inventory.json>` and a real disposable connection before promotion. The verifier reads the uploaded CA certificate through Cloudflare's API and compares its fingerprint with the selected root for the *actual* RDS instance CA, in addition to checking PostgreSQL scheme, endpoint and origin port 5432, TLS mode, cache, pool cap, and effective AWS security-group ingress against Cloudflare's current API ranges. Keep the token in a protected process environment; never store it in inventory or logs. A matching certificate is configuration evidence; successful `verify-full` Worker-to-RDS transactions are still required. All authority, authentication, grant/revocation, receipt, exact read and final search recheck clients must use this cache-disabled binding. Hyperdrive does not invalidate query cache after a write. The generated API, MCP and job workers in one cell share this single bounded Hyperdrive config.
4. Create the per-cell private R2 buckets with the manifest's location hints (`wrangler r2 bucket create <bucket> --location <hint>`), and separate Queue/DLQ pairs (`wrangler queues create <queue>`). Verify the actual R2 bucket location and access policy; keep public `r2.dev` URLs and custom domains off. Queues and job consumers must not be promoted until a durable projection handler exists. The generated scaffold handler throws rather than acknowledging work. No production business data may be written into development resources.
5. Create a private inventory JSON with environment, control/cell `rdsInstanceId`, 32-character `hyperdriveId` and `network: "public-tls"` fields. Set file mode `0600` and store it outside the repository or under ignored `.data/`. Optionally add distinct `routes.app` and `routes.mcp` HTTPS authorities. Each route must have the form `https://<hostname>` with no port, path, query or fragment. The hostname needs at least two lowercase ASCII DNS labels, each 1–63 characters, starting and ending with a letter or digit; the full hostname must be at most 253 characters. This syntax check does not prove domain ownership or DNS resolution. Render with `node scripts/topology.mjs render <environment> <inventory.json>`. Run `node scripts/verify-topology.mjs <environment> <inventory.json>` against live RDS/Hyperdrive and every attached AWS security group before any upload. This fails on wrong DB, region, backup retention, absent or stale latest restorable time, TLS mode, cache, connection cap, absent or unapproved ingress. Review the generated service, queue and R2 bindings; run `wrangler deploy --config <generated-file> --dry-run` for each Worker. Private cell and directory Workers have neither routes nor `workers.dev` exposure. App/MCP public routes are attached only when explicitly present in inventory. After building `@stateplane/app`, the synthetic `pnpm topology:dry-run` writes only under `.data/topology-dry-run/`; it never rewrites operator-rendered `.data/topology/` configs.
6. Deploy private directory and cells first; then job workers only after projection handling exists; deploy global gateways last. Check active version IDs and service bindings. The global app is still a scaffold, and API/MCP traffic must fail closed until STA-5 implements routing and authorization. Run exact-head disposable acceptance before promoting a production route. Do not equate a deploy dry-run with a Cloudflare transaction.

### Disposable transaction acceptance

For each target cell region, create an isolated PostgreSQL database with pgvector, a cache-disabled Hyperdrive config and a Preview Worker. Name the database `sta4_<first-16-head-hex>_<dev|prod>_<cell_with_underscores>` and the role `sta4_probe_<first-16-head-hex>`. The generator and Worker both use `deployment/topology.json` to admit the declared environment/cell pairs; production `eu-west` is not a target. Grant that role only the connection and schema rights needed for this disposable database; read back its effective grants, including default `PUBLIC` grants, before probing. Do not reuse a production database credential. Read back the Hyperdrive ID, origin host, database and role from the connected provider and match them to the generated Preview binding and issue/head cell. Verify the role's effective grants on the target database before sending a request that can create the probe table. The Worker checks `current_database()` and `current_user` before any DDL, so a misbound Preview fails before writing, but that identity check does not prove least-privilege grants.

The [qualification Worker](../deployment/workers/qualification.ts) gets its Wrangler configuration from `node scripts/qualification-config.mjs sta-4-<head>-<dev|prod>-<cell> <hyperdrive-id>`. The `dev`/`prod` segment separates same-region Worker and Preview names while retaining the full head within the 63-character Worker limit. Generated top-level and `previews` bindings carry the same `AUTHORITY`, disposable marker and expected database/role; Preview does not inherit top-level settings. Supply a private `PROBE_TOKEN` via `wrangler preview --secrets-file <0600-file> --config <generated-config> --name <same-config-name> --json`. Before POST `/qualify`, inspect the deployed Preview bindings, then call it with the bearer token. A config dry-run alone does not prove the live target or its grants.

The probe checks pgvector distance, transaction rollback, fresh reads from a second connection after committed mutations and observed session count. It deletes its row and verifies absence before reporting success. A failure returns HTTP 500 and logs only sanitized stage identifiers; cleanup and client-close failures also fail the probe. Inspect and remove residual rows from the disposable database before treating it as clean. Run concurrent requests up to the declared connection budget and compare `pg_stat_activity` with RDS `max_connections` headroom. Record timestamps, region/instance IDs, Preview IDs, sanitized result payloads, measured latency and pool exhaustion, then repeat after mutation to detect stale reads. A Railway disposable can prove a generic Worker/driver path but cannot prove Mumbai placement: [Railway's listed regions](https://docs.railway.com/deployments/regions) currently omit India. The final reviewer must use actual regional origins for that claim.

### Rollback and cleanup

Before a public route is enabled, remove any failed Preview, Worker version/binding, Hyperdrive, Queue/DLQ, R2 bucket and disposable database created for the attempt. Verify each is absent by ID. On a promoted release, remove or revert public routes first and confirm traffic fails closed; roll back gateway versions, then cell versions. Preserve RDS and backups until data/export and restore checks pass; deleting an instance with data is a separate controlled operation. Restore to a *new* RDS instance named `<original-instance-id>-restore-<lowercase-alphanumeric-token>`. The token must be at least eight characters and at most the lesser of 24 characters and `63 - original instance ID length - 9`; check the complete ID against inventory validation before provisioning. Verify the recovered SQL and pgvector, create a new cache-disabled Hyperdrive pointing there, re-render inventory and dry-run all configs before cutover. Do not silently redirect one cell to another region. Revoke temporary network rules, Preview tokens, database credentials and CI deployment credentials after the drill. An interrupted promotion resumes from live inventory and version IDs, never from assumptions about the last command's success.
