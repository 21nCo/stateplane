# Postgres authority (STA-5)

`migrations/002_authority.sql` owns fixed tables for spaces and placement fields, collections and accepted versions, collection grants, records, immutable events, unique reservations, declared typed index values, receipts, tombstones, projection outbox, and reserved source/claim identities. Migration 003 prevents edits to accepted collection versions and committed receipts. Every record child uses `(space_id, collection_id, record_id)` foreign keys; unique and typed values also reference their declarations. Source and claim payloads, links, schema validation, complete query/cursor behavior and public transports have later owners (STA-13, STA-7, STA-8, STA-9/10). The in-memory STA-2 oracle is not this adapter.

`PostgresAuthority` uses `pg.Pool` clients with `BEGIN`/`COMMIT`, transaction-scoped advisory receipt reservation, shared policy/placement/collection locks, conditional revision updates and database-enforced unique keys. It snapshots the authenticated scope before acquiring a client and keeps it fixed across confirmed retries. It never changes session scope or holds a client after its callback. Rollback runs before release; a failed rollback, ambiguous `BEGIN`, or ambiguous `COMMIT` discards the connection. A caught mutation error makes the transaction rollback-only, including when an insert or update already ran. Confirmed deadlock/serialization rollbacks retry the pure `mutate` request at most twice; arbitrary transaction callbacks are never retried. An ambiguous commit must be retried by the caller using the **same** idempotency identity and fingerprint. The saved receipt is returned only while the original write authorization remains current. `RECEIPT_PENDING` signals an in-flight matching identity. A fresh write in a `readOnly` space fails, while a committed authorized replay is allowed there; a `readOnly` collection denies both fresh writes and replays, including replay through another requested collection.

Receipt rows are inserted after callback work and the final authorization check, directly before `COMMIT`. Their timestamps and expiry come from the Postgres clock, and the receipt returned by `transaction` is finalized before the callback result is returned. The pending receipt map keeps private facts and gives callbacks detached copies, so changing a returned receipt or its nested fields cannot change a saved or same-transaction replay. This keeps a held transaction and a skewed application clock from consuming the retry window before commit. A caller must use the returned receipt after `transaction` resolves; timestamps observed inside its callback are provisional. Postgres cannot expose the exact future commit instant to a transaction, so a transport stall between final insertion and `COMMIT` can still consume part of a very short retention interval. Set retention above the maximum expected commit transport delay and client retry window. Grant expiry also uses the Postgres clock. The transaction-local pending receipt map preserves same-transaction replay and never survives client release.

The repository accepts canonical JSON **strings**, not caller-owned objects. It rejects noncanonical key order, malformed Unicode, nesting beyond 64 levels and values above 1 MiB in UTF-8; the SQL check also caps stored canonical record and event payloads. These are explicit initial operational choices for bounded CPU, stack, row and WAL growth, **not** measured Railway/Hyperdrive limits. The application must validate the restricted collection schema, normalize external/composite keys, encode collision-safe typed unique tuples, validate declared typed fields, and calculate the canonical request digest before calling the repository. `queryRecords`, `countRecords` and `existsRecord` share a scoped AND predicate compiler with 16 predicates; pages cap at 100 rows. Migration 004 compares UTC date-time index text as an instant key after removing the `Z` and insignificant fractional zeroes, under C collation; this preserves arbitrary fractional precision and leap-second ordering that `timestamptz` would lose. The application must validate UTC calendar/leap syntax before writing or querying these fields. STA-8 must apply declaration allowlists, signed cursors, sorts and full read policy. These caps are initial memory/query bounds, not provider capacity claims.

Provisioning and grant/policy writers must lock the `spaces` row and increment `policy_version`; placement writers also increment `placement_generation`. A mutation holds shared locks through commit and checks both versions at entry and before commit. Nonowner grant rows are locked through commit. The application still authenticates credentials, authorizes the requested target **before** repository access, validates mutation shapes, and rechecks policy at its boundary. The repository's owner comparison assumes a server-derived `principalId`, never a caller claim. New collection versions must be inserted before advancing `collections.schema_version` in one transaction. Migration history is digest-checked, numerically ordered and protected by a transaction advisory lock in `scripts/migrate.mjs`.

`record_events` stores immutable change facts; its trigger rejects UPDATE/DELETE. `projection_outbox` tracks mutable delivery attempts, state, error and availability and may be retried without rewriting the audit event or saved receipt. `claimOutbox` uses row locks and attempt fencing; `finishOutbox` also requires an unexpired lease, even before another worker reclaims the row. A claim takes 1 to 100 jobs with a caller-chosen 1 to 3600 second lease. These are initial bounds to limit one transaction's locks and stale-worker recovery delay, not measured provider limits. Receipts expire after the caller-configured `receiptRetentionSeconds`, which must cover the promised client retry window; expiry removes replay protection for that identity and permits a new request. Tombstones and their external/composite key reservations have no automatic expiry in v1. Event and outbox retention require a separately approved archival/erasure policy; no automatic pruning runs here. Database backup must retain base tables, migration history, WAL and outbox state together. A provider snapshot alone is not evidence of recoverability: restore into an isolated database and compare IDs, revisions, constraints, receipt and outbox rows before use. No point-in-time recovery interval is claimed by this code.

## Verification

Run `pnpm db:up && pnpm db:migrate && pnpm test:postgres && pnpm db:restore-smoke`. The focused test uses real pooled connections and checks competing revisions, unique conflicts, rollback effects, pending and lost-response replay, current grants, read-only behavior, typed predicates, and unchanged row counts. The restore smoke compares a populated local archive with a separate database and checks an enforced unique constraint. Run `pnpm db:migrate` again to prove the migration prefix is stable. These are local Postgres checks. Exact-head acceptance still needs Railway Postgres and Hyperdrive transactions, injected before/after-commit failures, Cloudflare Preview, connected provider readback and Aside Browser observations through the configured external workflow.
