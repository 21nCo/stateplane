# Postgres authority (STA-5)

STA-6 adds migrations 011 through 024 for the control placement directory, cell-local credential/principal mappings, one-use routing nonces, lifecycle audit and scoped space erasure, followed by provider revocation, staged and confirmed keys, directory backfill, issuance/cancellation journals, provisioning recovery, immutable audit guards, runtime leases, the completion fence and pending-index maintenance. The [owned-spaces contract](owned-spaces.md) defines synchronization and retry behavior. Migration 012 preserves ordinary immutable-fact triggers while permitting the table owner to delete one `deleting` space's facts through a restricted erasure routine; the deleted space tombstone and audit rows remain.

`migrations/002_authority.sql` owns fixed tables for spaces and placement fields, collections and accepted versions, collection grants, records, immutable events, unique reservations, declared typed index values, receipts, tombstones, projection outbox, and reserved source/claim identities. Migration 003 prevents edits to accepted collection versions and committed receipts. Migration 004 adds exact instant ordering; migration 005 removes the superseded text-time index, and migration 006 gives scoped outbox claims due-time ordering. Migrations 007 and 008 add transient receipt identity and collection-scope reservations. Migration 009 moves their lock and candidate probes into an invoker-rights Postgres routine. Migration 010 replaces that routine so a successful candidate INSERT/DELETE probe rolls back its own exception subtransaction: deleting the row alone leaves a unique-key conflict until outer transaction completion and could falsely disclose pending state. The routine restores the prior transaction-local lock timeout and grants no default PUBLIC execute access. A contender probes only currently authorized collection scopes before returning a pending response; uncommitted reservation rows never appear in a normal read. Migrations 005 and 006 each build the outbox claim index; both files have applied checksums, so consolidating them would break existing upgrades. Earlier populated 2,000-row local upgrades measured 005's build at 5–6 ms and the 006–007 migrator at 68–99 ms. Two current 006–008 runs measured 65–74 ms, including process startup. Those earlier measurements are local observations. A disposable Singapore Railway PostgreSQL 16/pgvector upgrade with 2,000 complete rows measured 005 at 494 ms and 006 at 515 ms. Concurrent scoped claim reads had no errors; the slowest of five 005 samples was 224 ms and of four 006 samples was 322 ms, versus 76–96 ms baseline. All seeded row checksums and the final index were preserved. This small nonproduction sample is not a capacity guarantee or an approved lock budget. The upgrade smoke compares complete rows and the final index with a fresh install and checks a scoped claim plan without a sort. Every record child uses `(space_id, collection_id, record_id)` foreign keys; unique and typed values also reference their declarations. Source and claim payloads, links, schema validation, complete query/cursor behavior and public transports have later owners (STA-13, STA-7, STA-8, STA-9/10). The in-memory STA-2 oracle is not this adapter.

Migrations 005 and 006 are applied in one transaction by `scripts/migrate.mjs`, so their table locks can block claims until the final migration commit. For an existing outbox and either pending index migration, the default runner acquires a `SHARE` table lock before checking emptiness and holds it through commit. The lock waits for in-flight writers and excludes new writes and claim updates, so the emptiness decision cannot race a commit. A default zero lock timeout is narrowed to five seconds for acquisition and restored before the DDL; an existing nonzero timeout remains in force. A timeout rolls back and is safe to retry. This five-second acquisition ceiling is a fail-closed migration choice, not a claim-latency or production availability target. If rows are present, the runner refuses before executing pending SQL. To upgrade such a database, stop claim workers and writers and verify that traffic is drained, then run the migrator with `STATEPLANE_POPULATED_INDEX_UPGRADE=drained`. Keep traffic stopped until commit and verify the migration ledger, complete row facts and final index before reopening it. The flag records an explicit offline operational choice; it does not itself drain connections or promise an online latency bound. A failed run rolls back the full migration transaction and can be retried with the same file hashes. Fresh installs and already-applied migrations need no flag. A true online index replacement would require a separately reviewed forward-compatible migration design; a later migration cannot remove the historical 005/006 lock window.

An isolated verified-TLS Railway PostgreSQL 16/pgvector qualification on this repair head seeded 2,000 and 100,000 complete record, event, receipt and outbox rows. It launched scoped claims after each index drop in the same transaction and observed relation lock waits through the final commit. At 2,000 rows, warmed claims were 61–70 ms and overlapping claims took 899 and 695 ms. At 100,000 rows, warmed claims were 92–132 ms and overlapping claims took 1,377 and 1,029 ms. The maximum added latencies, 829 and 1,245 ms, exceed the initial 250 ms engineering qualification target; no claim errored. The 100,000-row disposable fixture used a bulk-load mode that bypassed foreign-key triggers only during seeding, then restored normal mode and checked all event, outbox and receipt references before measurement. Both volumes preserved complete row checksums and the final scoped no-sort claim index. Default migrator refusal was observed before DDL at both volumes with unchanged migration history and facts. These nonproduction samples justify the offline guard, not a production scale or latency guarantee.

`PostgresAuthority` uses `pg.Pool` clients with `BEGIN`/`COMMIT`, shared space/collection policy locks, conditional revision updates and database-enforced unique keys. After requested-target authorization, a mutation inserts scoped and global identity reservations within the authority transaction. A competing insert uses a 50 ms transaction-local lock timeout. Before returning `RECEIPT_PENDING`, the contender proves the original collection is still authorized through the scoped reservation conflict; otherwise it denies the retry. The routine’s exception subtransactions restore transaction usability after a timed-out insert, and the reservation row is deleted in the same transaction immediately before commit. A rollback removes it automatically. Different identities can advance concurrently, while row revisions and unique constraints still select one winner. The 50 ms value is an initial per-probe bound on database lock waiting, not an end-to-end Hyperdrive latency promise. On a verified TLS Railway endpoint, a warm SELECT measured about 60 ms from this host; the prior 17-statement pending path took 1,565 ms. The new server-side path plus one-query grant locking used six statements and returned pending in 620 ms with three connections warmed. A cold additional connection added roughly 400 ms. The integration test keeps a 250 ms local floor and calibrates its remote deadline from measured round-trip time plus two 50 ms lock probes; it still rejects the prior 17-statement remote path. Placement, cold starts and load need separate operational SLO measurements. No runtime advisory lock or session-persistent scope is used. It snapshots the authenticated scope before acquiring a client and keeps it fixed across confirmed retries. It never holds a client after its callback. Operation admission closes when the callback settles; accepted mutations, outbox updates and reads drain before final checks and commit or rollback. Rollback runs before release; a failed rollback, ambiguous `BEGIN`, or ambiguous `COMMIT` discards the connection. A caught mutation error makes the transaction rollback-only, including when an insert or update already ran. Confirmed deadlock/serialization rollbacks retry the pure `mutate` request at most twice; arbitrary transaction callbacks are never retried. An ambiguous commit must be retried by the caller using the **same** idempotency identity and fingerprint. The saved receipt is returned only while the original write authorization remains current. A fresh write in a `readOnly` space fails, while a committed authorized replay is allowed there; a `readOnly` collection denies both fresh writes and replays, including replay through another requested collection.

Receipt rows are inserted after callback work and the final authorization check, directly before `COMMIT`. Their timestamps and expiry come from the Postgres clock, and the receipt returned by `transaction` is finalized before the callback result is returned. The pending receipt map keeps private facts and gives callbacks detached copies, so changing a returned receipt or its nested fields cannot change a saved or same-transaction replay. This keeps a held transaction and a skewed application clock from consuming the retry window before commit. A caller must use the returned receipt after `transaction` resolves; timestamps observed inside its callback are provisional. Postgres cannot expose the exact future commit instant to a transaction, so a transport stall between final insertion and `COMMIT` can still consume part of a very short retention interval. Set retention above the maximum expected commit transport delay and client retry window. Grant expiry also uses the Postgres clock. The transaction-local pending receipt map preserves same-transaction replay and never survives client release.

The repository accepts canonical JSON **strings**, not caller-owned objects. It rejects noncanonical key order, malformed Unicode, nesting beyond 64 levels and values above 1 MiB in UTF-8; the SQL check also caps stored canonical record and event payloads. These are explicit initial operational choices for bounded CPU, stack, row and WAL growth, **not** measured Railway/Hyperdrive limits. The application must validate the restricted collection schema, normalize external/composite keys, encode collision-safe typed unique tuples, validate declared typed fields, and calculate the canonical request digest before calling the repository. Replace and patch calls must supply complete `unique` and `indexes` arrays derived from the accepted resulting canonical object, including empty arrays where no declarations apply. Omitting either array is rejected before SQL so an update cannot silently release a live reservation or remove a query index. `queryRecords`, `countRecords` and `existsRecord` share a scoped AND predicate compiler with 16 predicates; pages cap at 100 rows. Migration 004 compares UTC date-time index text as an instant key after removing the `Z` and insignificant fractional zeroes, under C collation; this preserves arbitrary fractional precision and leap-second ordering that `timestamptz` would lose. The application must validate UTC calendar/leap syntax before writing or querying these fields. STA-8 must apply declaration allowlists, signed cursors, sorts and full read policy. These caps are initial memory/query bounds, not provider capacity claims.

Provisioning and grant/policy writers must lock the `spaces` row and increment `policy_version`; placement writers also increment `placement_generation`. A mutation holds shared space and collection locks through commit, then checks both versions again before commit. These locks conflict with policy and placement updates without blocking unrelated record writes. Nonowner grant rows are locked through commit. The application still authenticates credentials, authorizes the requested target **before** repository access, validates mutation shapes, and rechecks policy at its boundary. The repository's owner comparison assumes a server-derived `principalId`, never a caller claim. New collection versions must be inserted before advancing `collections.schema_version` in one transaction. Migration history is digest-checked, numerically ordered and protected by a transaction advisory lock in `scripts/migrate.mjs`, which runs through a direct administrative connection rather than Hyperdrive.

When the migration owner differs from the operational writer, grant that writer `INSERT` and `DELETE` on `receipt_reservations` and `receipt_reservation_scopes` plus the `SELECT` needed for reservation cleanup and readback. Both tables are empty after each successful transaction; do not grant them to the disposable qualification role. Also grant `EXECUTE` on `stateplane_try_reserve_receipt(text,text,text,text,text,text)` to that role; migrations 009 and 010 revoke the default PUBLIC execute grant. Verify these grants through the live operational Hyperdrive role after migration and restore.

`record_events` stores immutable change facts; its trigger rejects UPDATE/DELETE. `projection_outbox` tracks mutable delivery attempts, state, error and availability and may be retried without rewriting the audit event or saved receipt. A failed delivery waits at least five seconds before retry, doubling to a one-hour cap; these initial bounds keep a failing projection from being reclaimed on every poll and are not provider capacity measurements. `claimOutbox` uses row locks and attempt fencing; `finishOutbox` also requires an unexpired lease, even before another worker reclaims the row. A claim takes 1 to 100 jobs with a caller-chosen 1 to 3600 second lease. These are initial bounds to limit one transaction's locks and stale-worker recovery delay, not measured provider limits. Receipts expire after the caller-configured `receiptRetentionSeconds`, which must cover the promised client retry window; expiry removes replay protection for that identity and permits a new request. Tombstones and their external/composite key reservations have no automatic expiry in v1. Event and outbox retention require a separately approved archival/erasure policy; no automatic pruning runs here. Database backup must retain base tables, migration history, WAL and outbox state together. A provider snapshot alone is not evidence of recoverability: restore into an isolated database and compare IDs, revisions, constraints, receipt and outbox rows before use. No point-in-time recovery interval is claimed by this code.

An archived (`readOnly`) space accepts only the internal `system:projection` worker for existing, committed outbox jobs. It still rejects fresh record mutations. Workers must use the current policy version after archival; a claim made before the transition can be finished under the new version only while its lease and attempt fence remain valid. Suspension and deletion deny both claim and finish, and deletion erases remaining jobs. Collection deletion also denies worker admission. A projection adapter must recheck lifecycle immediately before an external provider effect; a prior claim alone does not authorize that effect.

## Verification

Run `pnpm db:up && pnpm db:migrate && pnpm test:postgres && pnpm db:upgrade-smoke && pnpm db:index-race-smoke && pnpm db:restore-smoke`. The focused test creates a disposable database, uses real pooled connections, and checks competing revisions, unique conflicts, rollback effects, pending and lost-response replay, current grants, read-only behavior, typed predicates, and resulting row counts. It drops that database after the run. The upgrade smoke seeds 2,000 records, events, receipts and outbox rows under migration 004, records and applies the hash-locked 005, then applies 006–010; it compares complete rows, migration replay, the final index against a fresh install and a scoped claim plan. The index race smoke starts 2,000 outbox rows in a separate uncommitted transaction, waits for the migrator's real relation lock, then commits or rolls back at both 004 and 005 prefixes; it also covers timeout, interrupted migration, drained retry and empty upgrade. Run the race smoke again with `PGOPTIONS='-c default_transaction_isolation=repeatable\ read'` and `PGOPTIONS='-c default_transaction_isolation=serializable'` to verify that administrative defaults cannot make the post-lock emptiness check stale. The migrator explicitly begins in READ COMMITTED before its first snapshot query and holds the writer-excluding lock through commit. Both smokes use disposable databases and private markers so a later run can remove databases left by interruption. The restore smoke seeds a separate disposable source, compares its populated 17-table archive with an isolated restored database, checks an enforced unique constraint, and drops both databases. Run `pnpm db:migrate` again to verify recorded migration history and checksums; recorded SQL is skipped, so this does not test SQL idempotency. Set `STATEPLANE_DOCKER_EXECUTABLE` to an absolute path if Docker is outside the standard installation paths. These are local Postgres checks. Exact-head acceptance still needs Railway Postgres and Hyperdrive transactions, injected before/after-commit failures, Cloudflare Preview, connected provider readback and Aside Browser observations through the configured external workflow.
