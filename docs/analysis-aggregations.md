# Interactive aggregations (STA-58)

`PostgresAggregations` (`packages/postgres/src/aggregations.ts`) answers bounded, typed aggregations over one collection's declared index fields in one statement snapshot, on analytical capacity apart from interactive authoritative reads. It is the second of five slices of STA-15, after the [analysis job storage](analysis-jobs.md) (STA-57). The application boundary exposes it as `StateplaneServices.analysis.aggregate`, which takes the spec as JSON text; no HTTP, CLI or MCP surface reaches it yet (STA-61). Long or complete analyses that need a pinned watermark are STA-59's jobs, not this.

## Spec

```json
{
  "where": [{ "field": "team", "kind": "string", "operator": "in", "value": ["red", "blue"] }],
  "groupBy": [{ "field": "team" }, { "field": "at", "bucket": { "unit": "day", "timeZone": "America/New_York" } }],
  "metrics": [{ "op": "count" }, { "op": "sum", "field": "score" }, { "op": "avg", "field": "score" }],
  "maxGroups": 100
}
```

- `where` is the exact query's scalar predicates, ANDed: the same shapes, validation and compiler (`predicateFilter`) as `records.query` and `records.count`, each over a ready filterable index of the predicate's kind. There is no OR, no join, no raw SQL and no user code: field names and values are bound parameters, operators and units are allowlisted.
- `groupBy` holds up to 3 dimensions; an empty `groupBy` is the same as none, one group of all matching records. A string, number or boolean index is grouped by value; a date-time index only by a time bucket (`hour`, `day`, `week`, `month`, `quarter` or `year`) in an IANA time zone, and only it is bucketed.
- `metrics` holds 1 to 16 of `count` (records, no field), `sum` and `avg` (number indexes), and `min` and `max` (number, string and date-time indexes).
- `maxGroups` defaults to 100 only when absent; `null` or any non-integer is `INVALID_ARGUMENT`.
- Every grouped or measured field must be a ready declared index (filterable or sortable); an undeclared, unindexed or pending field is `SCHEMA_CONFLICT`, and an operator a field's kind does not accept, or any malformed spec, is `INVALID_ARGUMENT`. The caller needs `records:read` on the collection, which is checked before the spec is validated. The whole spec, every predicate's field, kind, operator and value included, is validated, and checked against the collection's declarations and the database's time zones, before any capacity is taken or reported and before any of it reaches a query, so a malformed predicate is `INVALID_ARGUMENT`, never a schema conflict, and no caller hook (such as a `toPostgres` or `toJSON` on a field object) ever runs.
- `aggregateSerialized` takes the spec as JSON text of at most 32 KiB and parses it only after the collection is authorized; it works in every runtime, and the application service uses it. `aggregate` takes the spec as an object, which, as for the exact query ([versioned collections](versioned-collections.md)), is admitted only where the runtime detects proxies without running caller code, and is refused with `INVALID_ARGUMENT` elsewhere, such as in a Worker.
- Admission, bounds, the statement text, result formatting and the byte check use only built-ins captured when the package loads (`packages/postgres/src/intrinsics.ts`, or a module's own load-time captures of prototype methods), called through the captured `Reflect.apply`, or own code; every descriptor they hand to `Object.defineProperty` has no prototype. A later replacement of `Reflect.apply` or another global (`Number`, `JSON`, `Intl.DateTimeFormat`, `Buffer.byteLength`, `performance.now`, `Date.now`, `setTimeout`, `clearTimeout`, `Promise.race`), of an inherited method (on `Array`, `Map`, `Set`, `String`, `RegExp`, `Date` or `Promise`, an inherited `toJSON` and `Promise.prototype.then` included), or an `Object.prototype` member such as `get`, `set` or `value`, never admits a spec, changes a result, shrinks what the byte cap measures, skips a capacity bound or yields an untyped error. The same holds on the shared path every aggregation reaches outside the module, which `records.query`, `count` and `exists` share: the predicate compiler and its snapshot helpers (bound parameters appended as own slots, never with `Array.prototype.push`), the scope check and transaction cleanup (`AuthorityTransaction.close`), the request snapshot, the scalar string and instant checks, the transaction helper (`transact`, through its commit and rollback) and the commit deadline (`commitBeforeDeadline`), whose COMMIT is reported as of unknown outcome only once it was dispatched. The covered paths are exactly the list below.
- A bucket's `timeZone` is an IANA name the database's time zone database knows. PostgreSQL reads a zone name as a [`timezone_abbreviations`](https://www.postgresql.org/docs/17/datetime-config-files.html) entry, a fixed offset, before its time zone database, so `CET` would stay at +01:00 all summer. A name that is also an abbreviation there (`CET`, `EET`, `MET`, `WET`, `EST`, `MST`, `HST`, `PST` with the `Default` set) is refused with `INVALID_ARGUMENT`; name the region's zone (`Europe/Paris`). `UTC`, `UCT`, `Zulu` and `GMT` name UTC either way: they run as `Etc/UTC`, and the result's `bucket.timeZone` reports the zone that was used.

These paths, in `packages/postgres/src`, are the guarantee's whole extent (`*` is a whole module apart from its load-time captures, `Class.method` one method). `test/covered-paths.js` holds the same list: `test/intrinsics-guard.test.js` fails if any of them names a live global or calls an inherited method again, in any property syntax or spacing, or if this list and that one differ.

## Semantics

| Aspect | Rule |
| --- | --- |
| Records | The collection's live records (deleted ones never count) matching every predicate |
| Null and missing | Kept apart: a group key is `{ kind: 'value', value }`, `{ kind: 'null' }` (the field holds JSON null) or `{ kind: 'missing' }` (the record lacks it). Groups order by value ascending (strings by UTF-8 bytes, numbers numerically, false before true, buckets by start), then null, then missing. A field metric reports `values`, `nulls` and `missing` counts and is computed over the values only |
| Count | Exact |
| Sum | Exact: PostgreSQL `numeric` over each stored value (the decimal JavaScript writes for it), as a plain decimal string without trailing zeros; `"0"` without values. So 0.1 + 0.2 is `"0.3"` |
| Average | Derived: the exact sum divided by the count of values, rounded half away from zero to 20 significant digits, as a plain decimal string; null without values. The metric says `semantics: 'derived'` and its precision |
| Minimum, maximum | Exact, in the field's own type: numbers as JSON numbers, strings by UTF-8 byte order, date-times by instant (fraction compared as a decimal, a leap second after 23:59:59) as the stored canonical instant |
| Time buckets | Derived, by PostgreSQL's time zone database (`date_trunc` in the zone), IANA rules only. A bucket's key is its start instant (`value`, UTC) and its local start with its UTC offset (`local`), both in proleptic Gregorian ISO 8601 years: a bucket starting in 1 BC (an instant early on 0001-01-01 in a zone west of UTC, or one east of UTC bucketed by its local day) is year `0000`, and a local start past 9999 (late on 9999-12-31 in a zone east of UTC) is written expanded, `+010000`. Day, week (ISO, from Monday), month, quarter and year buckets start at local midnight, so a DST day is 23 or 25 hours long; where a DST change skips midnight (America/Santiago), that day's bucket starts at the first local instant, 01:00. An hour bucket is a local wall-clock hour at its members' own UTC offset, so the two 01:00 hours of a fall-back night stay apart; where a shift is not a whole hour (Lord Howe's 30 minutes), an hour bucket's start can precede the first instant the zone's clock shows in it. A stored fraction past microseconds is cut, never rounded into the next second, and a leap second (23:59:60) falls in the minute it ends |

The result reports `source` (space, collection, `records: 'live'`, the predicates, and the policy version and placement generation it was admitted under), `collection` (the schema version read and the declared kind and accepted version of each grouped, measured or filtered field, once each, in that order), `snapshot` (`scope: 'statement'` and `takenAt`, the statement's start), each dimension's and metric's `semantics`, every group, and `complete: true`.

## One statement snapshot

The groups, metrics, their sizes and the cap checks are one SQL statement, so every number in a result comes from one snapshot, whatever commits meanwhile. It runs in one `READ COMMITTED` transaction that first share-locks the space at the admitted policy version and placement generation, the collection and a key's grant (as `AuthorityTransaction.checkScope` does for every reader), so a schema revision, lifecycle, policy or placement change or grant change cannot commit between the declarations read and the statement; record writers take the same share locks and are not blocked. The transaction ends with the same credential recheck as `records.count`, bounded by the statement time: a provider that has not answered by then fails the aggregation with `PROVIDER_UNAVAILABLE`, retryable, and rolls it back, and the session it was given refuses any query its late answer makes. A cap or limit failure rolls everything back: there is no partial result.

## Budgets

| Budget | Initial value | On excess |
| --- | --- | --- |
| Groups | `maxGroups`, 1 to 1,000, 100 by default | `AggregationLimitError` `groups`, code `RATE_LIMITED`, not retryable |
| Result bytes | 262,144 bytes of `groups` as JSON text: every key, count and metric value as returned, rounded averages included | `bytes`, `RATE_LIMITED`, not retryable |
| Statement time | `statement_timeout` 5,000 ms (a service option, 1 to 15,000 ms) | `time`, `RATE_LIMITED`, not retryable: the statement is cancelled |
| Analytical slots | Derived from the cell's origin connection limit (below) | `slots`, `BACKPRESSURE`, retryable, at once (nothing waits) |
| Analytical session | 2,000 ms to check one out of the analytical pool (`checkoutMs`), for each attempt and the slot provisioning | `slots`, `BACKPRESSURE`, retryable. The expired checkout stays counted against the pool's slots until the pool answers it, so retries meanwhile are refused at once; a session that arrives then is released unused (closed, if its release throws) and the reservation given back |

`AggregationLimitError` extends `AuthorityError`, so transports map its stable code as for any read; its `limit` names the budget. The statement also runs without parallel workers (`max_parallel_workers_per_gather = 0`), so one slot is one database backend. The statement sizes each group by a lower bound of its JSON (its key kinds and string and boolean keys, counts, sums and string and date-time extremes, each as long as in the JSON or shorter) and returns no groups when that alone passes the cap; the formatted groups are then measured in full before anything is returned.

## Analytical capacity

An aggregation's analytical work runs only on analytical capacity:

- Each cell has `analyticalSlots(originConnectionLimit)` slots: one fifth of the cell's configured Hyperdrive origin connections (5 to 20 in the topology schema), so 1 at today's 5 and 4 at 20, and a space may use half of them, at least 1. The jobs Worker holds up to half of a cell's origin connections and the API and MCP Workers the rest ([durable outbox](durable-outbox.md)), so at 5 the interactive reads keep at least 2 of their 3 under any analytical load.
- Aggregations run only on a cell's analytical pool, a pool of its own sized to the cell's slots (`AggregationCell.pool`; `ServiceCell.analytics` in `postgresServices`). `PostgresAggregations` refuses, at construction, a cell whose analytical pool is its admission (interactive) pool. A cell without one (`pool: null`, or a cell the adapter's map omits, which is authorized on the `PostgresSpaces` adapter's interactive pool for that cell) runs no aggregation: each is still authorized and validated first (so a caller without `records:read` gets `FORBIDDEN`, a missing collection `NOT_FOUND`, a malformed spec `INVALID_ARGUMENT`), then fails with `PROVIDER_UNAVAILABLE`, not retryable, rather than borrow the interactive pool.
- Before taking any capacity, an aggregation authorizes the collection and the caller's grant in one short transaction on the interactive pool (`AggregationCell.admission`), as any read is admitted, then validates its spec and, in the same transaction, resolves its time zones and checks every field against the collection's declarations, so a key without `records:read` or a missing collection gets `FORBIDDEN` or `NOT_FOUND`, a malformed spec or an operator its field's kind does not take `INVALID_ARGUMENT`, and a field that is not a ready declared index `SCHEMA_CONFLICT`, never `BACKPRESSURE` or `PROVIDER_UNAVAILABLE`, and none holds or waits on a slot. This admission is the only interactive work an aggregation does.
- In a process, at most the cell's slot count of aggregations run at once on each analytical pool, counted per pool whichever `PostgresAggregations` or composed services started them; another is refused before it takes an analytical connection.
- In the database, an aggregation holds a free (or lapsed) slot of the cell and one of the space in `analysis_cell_slots` and `analysis_space_slots` by row lock (`FOR UPDATE SKIP LOCKED`) for its transaction, after its scope locks (a purge locks its space before its slots). The slots are taken right after the scope locks, before the declarations are read and checked again and the statement runs, so all of that work, and every aggregate statement, runs under a held slot. When none is free and fewer slot rows exist than the limit allows, the missing ones are added up to the limit in a short transaction of their own, which first locks and checks the scope again (a space suspended or deleted meanwhile gets its typed authority error), and the aggregation retries once; rows past a lowered limit are ignored.

What is bounded, precisely: aggregate statements and the work around them are bounded by the database slots across every process and isolate, so at most the cell's slot count run at once and at most the space's slot count in one space. Analytical connections are bounded per process (isolate) by its analytical pool's size and by the in-process slot count; an attempt that finds no free database slot holds its analytical connection only for its scope locks and the slot lookup, then is refused at once. The admission transaction is one short interactive transaction, like any read's.

## Evidence

`test/integration/analysis-aggregations.test.js` (in `pnpm test:postgres`) checks every result against an independent reference oracle written in plain JavaScript from the data the tests wrote: decimal sums and averages with `BigInt` long division, buckets with `Intl` in the requested zones, its own null and missing rules and ordering. The generic fixture mixes nulls and missing fields, decimals whose float sum is inexact, magnitudes from 5e-324 to 1e21, instants around DST changes in New York, Berlin, Lord Howe and Kolkata, a leap second and fractions past microseconds, and replaced, patched and deleted records. A single writer replaces, creates and deletes records while aggregations run, and each result must equal the oracle at one committed state. The suite also covers the spec allowlist and refusals, authorization before capacity, the serialized entrypoint in a runtime without proxy detection, replaced built-ins in the module and on the shared predicate compiler, summer instants against same-named abbreviations, the group, byte (counts and averages as returned) and time caps with typed errors, the in-process slots shared by two services composed on one analytical pool, the cell and space slots across two service instances, bounded checkout of the first attempt, the provisioning and the retry with late sessions released, declaration checks before available, saturated and unconfigured capacity, an empty `groupBy`, filter-only fields in `collection.fields`, a replaced `Reflect.apply` with `Object.prototype` descriptor pollution through every aggregation and record reader, and interactive reads under saturating analytical load through the composed application services.

Measured locally on PostgreSQL 17 (pgvector image), warm cache: a two-field grouped aggregation over 60,000 records took a median 68 ms serially and 65 ms with two parallel workers, so the analytical budget gives up nothing measurable by forgoing them. With two composed application services (`postgresServices`, each with a 2-connection interactive pool and a 1-connection analytical pool, as two isolates) each driving six concurrent aggregation loops over those records at an origin limit of 5 for 2.5 s, at most one aggregation statement ran at a time (14 answered, 1,706 refused with `slots`), while interactive `records.count` and `records.get` pairs through the first service's own interactive pool took a median 18.3 ms and at most 53.1 ms. These are local observations, not Railway or Hyperdrive capacity claims; STA-60 measures the target and records the limits.
